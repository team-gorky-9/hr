# Контрольный набор: карточка и объяснимая оценка

**Все данные синтетические** (`"synthetic": true`). Учебный профиль не основан на должностной инструкции: порог «24 месяца коммерческого опыта» существует только здесь. Реальных резюме и персональных данных в наборе нет.

Набор отвечает на вопрос «что должна выдать оценка на этом очищенном тексте». Он нужен:
- **импорту (Денис)** — какой очищенный текст подать и какие границы цитаты должны совпасть;
- **профилям требований (Давид)** — одинаково ли мы понимаем основание `met` / `not_met` / `unknown`;
- **макету (Маша)** и **данным интерфейса (Ася)** — видимые значения из раздела `ui` каждого случая;
- **этапу 1** — эталон для тестов оценивания. Модели и её вызова в наборе нет.

Постановка: `hackaton/hq/tasks/stage-0b-02-assessment-fixtures.md`.

## Устройство `py-9001.json`

| Раздел | Что внутри |
|---|---|
| `candidates`, `texts` | Кандидаты и версии очищенного текста. `text` — ровно то, что получает модель (NFC) |
| `profile` | Учебный профиль: одно обязательное формальное требование опыта и одна компетенция с индикатором «Писал автоматизированные API-тесты» |
| `missing_vocabulary` | Закрытый список формулировок пробелов. В `CandidateCard.missing` и в `gap` проверки — только они |
| `cases[]` | Случаи: вход, ожидаемая карточка, предложенная оценка (`assessment`), ожидания (`expect`), видимые значения (`ui`) |

**Идентификаторы.** `id = uuid5(uuid_namespace, key)`. Ключ читается человеком (`py-9001/text/base`, `py-train/requirement/experience-commercial-24m`), UUID проверяется скриптом. В базе UUID выдаёт загрузчик. Тест БД показывает, как сопоставить одно с другим.

**Границы цитаты** — в кодовых точках Unicode, как срез Python: `text[start:end] == quote`. В `ui` есть ещё `utf16_start` / `utf16_end` — те же границы для JavaScript, где символ вне BMP (эмодзи) занимает две единицы. Подсвечивать в браузере нужно по ним (случай `C5-non-bmp`).

**`assessment`** — то, что предложила бы модель. **`expect`** — чему верим после проверки:
- `verdicts` — вердикт по каждой цитате: `ok`, `quote_not_at_offsets`, `stale_text_version`, `foreign_text`, `unknown_text`;
- `effective` / `issue` — вывод «выполнено / не выполнено» без годной цитаты понижается до `unknown` с причиной `missing_evidence` или `invalid_evidence`;
- `formal_result` — итог по обязательным требованиям. `null` — если оценки нет совсем;
- `refusal` — почему оценки нет: `model_unavailable`, `profile_not_approved`. Это **не** `unknown`: `unknown` значит «проверили, сведений не хватило», отказ — «проверки не было»;
- `db_v1` — что сейчас делает `save_assessment` с этой оценкой: `accepted` + итог, `rejected`, `not_called`.

**`enforced_by`** — кто отвечает за ожидание:
- `schema` — Pydantic-схемы;
- `db_v1` — функции доступа базы v1.0, уже работает;
- `stage_1` — ожидание этапа 1. База v1.0 такую оценку сохраняет, где проверять, ещё не решено.

## Что этот набор не утверждает

- Значения `params` требования опыта (`schema_version`, `scope`, `minimum_defined`, `min_months`) — предложение Давида, контрактом не утверждены.
- `competency_scores.level` везде `null`, кроме синтетического C4: шкала не согласована.
- Ранг и эталонный уровень компетенции не заданы (`null`): в учебном профиле их нет, а БД v1.1 разрешает их не заполнять.
- В тесте сверки профиль загружается через `create_requirement_profile` как учебный (`is_synthetic`), поэтому в БД он всегда черновик: учебный профиль утвердить нельзя. `save_assessment` статус профиля не проверяет, поэтому на результат сверки это не влияет.
- Доказательство хранится по компетенции (`competency_scores`), а не по индикатору. Индикатор указан ключом рядом с оценкой.
- Качество модели на архиве набор не измеряет.
