## Загрузка из самостоятельного клона

Достаточно файлов этого репозитория. Внешний архив, штаб, модель и ключ LLM не нужны. Установите зависимости и настройте `DATABASE_URL` по корневому README. На новой PostgreSQL с pgvector подготовьте схему и справочники:

```console
python -m alembic upgrade head
python -m app.db.seed
```

Одна команда проверяет оригиналы и загружает все шесть профилей через публичный API requirements-01:

```console
python -m scripts.load_all_six_profiles --commit --created-by david
```

JSON-отчёт содержит `position_code`, UUID профиля и должности, версию, статус, `is_synthetic`, источники с редакциями и счётчики. Без `--commit` выполняется полная проверка с откатом; UUID такого отчёта не сохранены. Ошибка любого профиля откатывает весь пакет. Повтор фиксированной версии — `version_conflict`, без частичной загрузки или перезаписи истории.

Если старый пакет уже загружен, консультант v4 создаст конфликт. Для перехода на существующей БД используйте публичный `load-package` с отобранными новыми профилями (Python v6 и четыре v1), сохранив полный манифест и оригиналы. Консультанта v4 повторно не загружайте. Не удаляйте старые профили и оценки ради повторного запуска.

Отдельное рабочее утверждение — только после содержательной сверки, с существующим активным HR/admin и конкретным основанием:

```console
python -m app.requirements approve <profile_id_из_сохранённого_отчёта> --approver <login> --basis "Проверены ДИ, применимость и условия этой версии" --commit
```

Утверждение архивирует прежний approved той же должности и контура. Пакет не создаёт утверждающего. Новые редакции вне фиксированного пакета можно передавать через `python -m app.requirements load <draft.json>` в формате `requirement-draft/1.0`: версия назначается автоматически. [Контракт загрузчика](../../../docs/contracts/requirement-loader.md).

## Принятые содержательные решения

- **Источники:** ДИ всех шести должностей и матрица консультанта. Файлы «Вакансия.txt» исключены по прямой инструкции Давида. Поэтому нет года Junior, диапазона «1–3», портфолио, React/Vue/Figma и других дополнительных требований только из публикаций. Старый [двухпрофильный пакет](../profiles.draft.json) неизменён; Python с изменённым составом требований выпущен как v6.
- **Применимость:** Давид подтвердил использование выданной ДИ дизайнера для данного кейса Junior UX/UI. Требование опыта P201 и обучение младших P128 сохранены. Временное замещение P194 — организационное правило сотрудника, учтённое в реестре покрытия; оно не добавляет самостоятельное требование руководящего стажа.
- **Опыт:** у IT требуется релевантный опыт без числового минимума. Работа, стажировка или договор с собственными соответствующими задачами могут его подтвердить. Учебный проект может подтверждать навыки; без рабочего контекста опыт остаётся `unknown`. Явное отсутствие опыта — `not_met` соответствующего условия. Ни один из исходов сам по себе не меняет этап отклика и не запрещает руководителю рассматривать дообучение. Новая формула ранжирования здесь не вводится.
- **Образование:** Python/Junior — высшее техническое либо явно указанный студент старших курсов; QA — высшее либо студент старших курсов, без добавления технического направления. Примеры технических направлений унаследованы из принятого Python v5 и не являются исчерпывающим справочником. Неоднозначные направления и номер курса без явного статуса требуют уточнения.
- **Frontend и UX/UI:** профильное образование, включая курсы повышения квалификации. По ответу HR курсы принимаются после проверки документа в ФРДО. Полное условие сохранено как `kind=other`, `verification=documents`, `check_stage=interview`: текущий `params 0.1` не выражает такую альтернативу автоматически. Сотрудник проверяет программу, соответствие роли и документ; отсутствие записи при поиске требует уточнения. Эта строка не участвует в первичном формальном итоге по резюме. Автоматического подключения к реестру нет.
- **Группировка:** новые IT-профили имеют 5–6 авторских групп, `origin=team` с основанием; строки условий и навыков — `origin=source` с цитатами. У Python сохранены восемь принятых содержательных групп. IT-ранги и проценты пустые. У консультанта сохранены пять компетенций и диапазоны матрицы, включая ДК 100–100, а также принятые исключения из счётчиков. Доля подтверждённых индикаторов не равна вероятности успешного найма.

Это зафиксированные решения подготовки данных, а не утверждение профилей уполномоченным сотрудником. Перечисленные в ДИ правовые акты перенесены как источник; их актуальность и применимость отдельно не исследовались. Знание права и личные качества не устанавливаются по стилю резюме.

## Происхождение и полнота

[`sources.json`](sources.json) хранит SHA-256 исходных файлов, редакции и полный адресованный текст. Оригиналы находятся в `originals/`; персональных резюме здесь нет. `P<n>` — номер абзаца `w:p` в `word/document.xml`, включая пустые абзацы в нумерации. Цитаты хранят исходный текст, заголовок индикатора может быть нормализован.

[`coverage.json`](coverage.json) учитывает каждый непустой абзац каждого источника: строка профиля, пояснение `source_notes` или контекст. Реквизиты, заголовки, права работника, организационное замещение, ответственность и нормы внутреннего распорядка не превращаются автоматически в независимые условия найма. Повторные формулировки исполнения обязанностей не создают дополнительные веса. Редкое знание правил обработки ПДн в конце Junior-ДИ P201 сохранено в группе SECURITY на интервью и объединено с P104 через `same_as`.

`source_notes` сохраняются в файловом пакете; публичный загрузчик проверяет их цитаты и сообщает число, но не создаёт из них условия оценки. Прочие редакторские поля тоже перечислены в `review_fields`. Загруженные строки сохраняют происхождение, этап, обязательность, способ проверки и `acceptance`.

Проверка без базы:

```console
python -m scripts.verify_all_six_profiles
```

Проверки на тестовой PostgreSQL с pgvector (`TEST_DATABASE_URL` указывает отдельную БД с окончанием `_test`; тесты пересоздают её схему):

```console
python -m pytest tests/test_all_six_profiles.py -q
```

## Один отклик — два профиля

[`example-junior-response.json`](example-junior-response.json) — явно **синтетический** отклик: окончен бакалавриат по программной инженерии, на стажировке выполнялись Python/SQL-задачи, прямо указано отсутствие опыта тестирования ПО. Тест задаёт извлечённые факты контролируемым ответчиком; качество распознавания живой моделью не измеряется.

| Проверка | Junior Python v1 | QA Manual v1 |
|---|---|---|
| Образование | `met`: техническое высшее, ДИ P192 | `met`: высшее, ДИ P185 |
| Релевантный опыт | `met`: стажировка с Python/SQL-задачами, ДИ P193 | `not_met`: явное отсутствие опыта тестирования, ДИ P186 |
| Профессиональные вопросы | Python P98, данные P117, ПДн P201 | Тест-дизайн P92, тест-кейсы P110, дефекты P114 |
| Решение о кандидате | Остаётся у руководителя | Остаётся у руководителя; этап не меняется |

Потребитель передаёт UUID выбранного профиля оценщику. Результат сохраняет этот UUID; профиль задаёт условия и источники. Образование здесь подтверждается по резюме предварительно, документы проверяются человеком. Вопросы интервью относятся к пробелам конкретной строки и не являются подтверждением навыка.

Отдельный пример — «Сметчик» в папке консультанта: наличие `hr-consultant` не подтверждает соответствие исходного отклика. Существующая политика возвращает `mismatch/different_role`; исходная оценка не должна подменяться кросс-сравнением. Задача requirements-03 остаётся владельцем маппинга публикаций.

После загрузки Илья получает UUID/версии из сохранённого отчёта и эти два примера; Денис и Ася — происхождение, этап, способ проверки и исходные цитаты. Тестовые UUID из отчёта проверки не являются идентификаторами профилей на стенде. [Протокол проверки](../../../docs/reports/requirements-02-six-profiles.md).
