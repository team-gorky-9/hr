## Стаж

Учебный порог `synthetic.py.experience` — 24 месяца общего коммерческого опыта. Он не переносится в реальную ДИ Python: `relevant_role` без численного минимума проверяется отдельно.

Месяцы считаются включительно, пересечения один раз. `2021-01–2024-01` даёт 37 месяцев. Для текущей работы вход `as_of=2026-11` фиксирован в примере; месяц запуска не извлекается из резюме. В рабочем расчёте он должен сохраняться с основанием результата.

Для каждого периода строятся гарантированный и возможный календарные промежутки. L получается объединением гарантированных, U — возможных. Самое позднее начало и самый ранний конец дают гарантированный промежуток; если начало позже конца, он пуст. Для U берутся самое раннее начало и самый поздний конец. Отсутствие границы без признака текущей работы даёт L=0 и U=бесконечность для этого периода до учёта его вида.

| Периоды с подтверждённым рабочим видом | L | U | Исход при 24 |
|---|---:|---:|---|
| 2022–2022 | 0 | 12 | not_met |
| 2022–2022 и 2022–2022 | 0 | 12 | not_met |
| 2022–2022 и 2023–2023 | 0 | 24 | unknown |
| 2019–2023 | 38 | 60 | met |
| 2021 — 2023-06 | 19 | 30 | unknown |

**Исправление первоначального ответа:** L для одного года теперь 0, не 1. Это гарантированные месяцы с определённым положением на календаре, а не просто минимальная возможная длина любого периода.

Коммерческий характер подтверждается оплачиваемой работой на работодателя, независимо от типа организации. Правило Ильи для `total_commercial`:

| Вид записи | В L | В U |
|---|---|---|
| work, contract | да | да |
| internship, неизвестный | нет | да |
| project — учебный или личный | нет | нет |

Стажировка по трудовому договору с явной цитатой классифицируется как work. Неизвестный вид не разрешено автоматически заменять на work. Классификация должна иметь текстовое основание; `Experience.kind` ещё не добавлен в действующую карточку этой ветки.

По периодам: L ≥ T → met; конечная U < T → not_met; иначе unknown. Пустой раздел или «Не указано» всегда unknown. Отказ по конечной верхней границе относится к заявленной истории и подписывается «по резюме».

Явное заявление «общий коммерческий опыт N лет» даёт S=round(N×12). Оно проверяется отдельно от периодов. Одинаковые исходы допускают общий результат с сохранением расхождения чисел. Разные исходы → unknown, `experience_conflict` и ручная сверка. Если периоды дают unknown, а S входит в [L,U], допустим исход по заявлению; если вне интервала — конфликт.

Заявление только об **общем** опыте даёт верхнюю границу коммерческого: «общий опыт 1 год» → not_met, «общий опыт 3 года» → unknown при T=24. Нельзя интерпретировать всякий `experience_years` как точный коммерческий стаж; учитывается цитата. Комбинации такого верхнего ограничения с противоречащими периодами в этих примерах не задаются как новый алгоритм.

Реальный `relevant_role` без минимума: Илья считает рабочим контекстом работу, стажировку или договор с релевантными обязанностями и цитатой; учебный/личный проект или неясная роль → unknown; not_met только при явном отрицании. Содержательную применимость этого правила к реальному профилю участник ещё проверяет с Родионом (Р7).

## Счётчики вместо балла

До утверждения шкалы `competency_scores.level=null`, проценты не вычисляются. Эталонные диапазоны консультанта сохраняются как данные источника. Счётчик показывает подтверждённость по имеющимся свидетельствам, а не процент профессиональной пригодности.

На screening используются статусы индикаторов: «подтверждено по резюме», «противоречит», «нет сведений». Для подтверждения или опровержения нужна цитата, содержательно удовлетворяющая критерию; само наличие любой цитаты недостаточно. Обязательные и желательные считаются отдельно.

- `excluded_from_scoring=true` не входит в Y; показывается отдельно как «не оценивается».
- `check_stage=interview` не входит в Y резюме; показывается отдельно «на интервью: K».
- Остальные применимые индикаторы/группы дают Y обязательных или желательных. X — число подтверждённых единиц той же категории.
- После интервью результаты и счётчики имеют основание interview, не смешиваются с resume; сохраняется предыдущая версия оценки.

## Группы same_as

`same_as` — общий стабильный непустой ключ группы на каждой её строке, не ссылка-цепочка на соседнюю строку. Группирование выполняется внутри профиля. В примере используется `py.same-as.personal-data-law`. Идентификаторы исходных строк и их источники сохраняются.

Валидатор пакета отклоняет группу, если строки находятся в разных компетенциях, имеют разные `check_stage` или хотя бы одна исключена из оценки. Разная обязательность разрешена: группа обязательна, если обязательна любая строка. Одна группа — одна единица в компетенции; сводка профиля суммирует компетенции. Одна цитата сама по себе не означает дубль разных навыков.

| Статусы участников | Статус группы |
|---|---|
| Есть подтверждение, остальные без сведений | подтверждено |
| Есть противоречие, подтверждений нет | противоречит |
| Есть и подтверждение, и противоречие | противоречит + ручная сверка |
| Все без сведений | нет сведений |

Контрольный пример для будущего счётчика: две screening-строки одной компетенции в same_as, первая обязательна и подтверждена, вторая желательна и без сведений. Ожидание: обязательные X=1/Y=1, желательные X=0/Y=0. Если вторая явно опровергнута, X обязательных=0/Y=1, противоречит=1, ручная сверка=true. Если обе без сведений, X=0/Y=1, нет сведений=1. Это ручные ожидания; код агрегации остаётся в модуле Ильи.

В Python v4 связаны только `py.di.P112` и `py.di.P209`: обе строки требуют знания законодательства о защите и обработке ПДн, обе в SECURITY и на интервью. `py.di.P134` о применении требований не объединена со знанием. Прочие совпадения требуют содержательной сверки; отсутствие same_as не является доказательством отсутствия повторов.

## Основание результата и совместимость

Для `verification` и `basis` Илья подтвердил один словарь: `resume`, `documents`, `interview`, `test`. Значение `document` больше не используется. verification описывает способ проверки требования, basis — фактическое основание результата. Известный пример предварительности: basis=resume при verification=documents → «по резюме, нужен документ»; документальная проверка создаёт новую версию с basis=documents. Полный порядок «силы» всех четырёх способов пока не задан; автоматически строить иерархию нельзя.

Расширение карточки разрешено Родионом, но точный контракт — за Денисом: закрытый level с level_raw, нормализация старых значений, unknown при нераспознанном уровне, статус и курс обучения, Course.kind и прочие поля. В этой ветке `app/schemas/card.py` не меняется. Неизвестный уровень кандидата отличается от неподдерживаемого правила: последнее запрещает всю оценку (`rule_unsupported`).

В случаях ревизии 3 `period_months_lower/upper`, `period_kinds`, `statement_scope`, `statement_months`, `statement_upper_months`, `value_discrepancy` и `experience_conflict` — ручные ожидания рядом с карточкой, не новые поля БД. Бесконечная U представлена `period_months_upper=null` вместе с `period_months_upper_unbounded=true`. Годы без месяцев остаются в тексте и card_limitations, пока схема не расширена.

Загрузчик Дениса на проверенном коммите `09d32ef` не сохраняет same_as и check_stage. Совместимость преобразования не доказывает, что оценщик получит эти поля из БД. Хранение оснований, альтернатив, результатов индикаторов и групп остаётся задачей владельцев модулей.
