# Черновые профили требований

Два реальных профиля для сверки команды: консультант сектора подбора кадров (`hr-consultant`) и Python-разработчик (`python-dev`). Пакет содержит исходные цитаты, правила, индикаторы, способы проверки и явные нерешённые вопросы. Все профили `draft`; рабочие рекомендации по кандидатам запрещены до утверждения. Здесь нет алгоритма оценки или загрузчика БД.

## Файлы

- [profiles.draft.json](profiles.draft.json) — канонические данные черновиков и вопросы команде. 4 формальных условия; у консультанта 5 компетенций и 54 индикатора (40 исходной матрицы и 14 дополнений из ДИ), у Python 8 предложенных групп и 53 индикатора из ДИ и вакансии. Примечания об источниках не являются оцениваемыми условиями.
- [sources.json](sources.json) — 4 документа, пути относительно корня архива без `Кадры/`, SHA-256 и текстовые абзацы. Номер `P` — адрес в OOXML, не страница. `L` — номер строки TXT. Порядок извлечения описан в манифесте.
- [synthetic/cases.json](synthetic/cases.json) — отдельный учебный профиль и 24 ожидаемых случая: стаж, альтернативы образования, релевантность, ошибка версии/ключа. Результаты модели здесь не записаны.

Исходники: [архив «Кадры.zip»](https://yadi.sk/d/hi1Jqc2lkE2tzw). SHA-256 архива: `801efb82667a63d5d2370e6d39b00c74bea5069a3643472d41f476348a559baf`. Резюме кандидатов не включены. Текстовые снимки не подтверждают наличие подписей, юридическую актуальность или полномочия утверждающего.

## Как читать строки

Каждая строка имеет устойчивый `key`, нормализованное описание, `source_refs` с хешем, адресом и дословной цитатой, происхождение `origin`, обязательность, способ и этап проверки, достаточное подтверждение/явное невыполнение/недостаточность данных, ссылки на вопросы. Цитата сохраняется точно; нормализованное название не выдаётся за дословный текст.

Файловый формат `requirement-profile-review/0.2` следует последнему решению Дениса. Оба реальных профиля имеют версию 2; ключи условий, индикаторов и контрольных случаев сохранены. Учебный профиль использует ту же структуру `formal_requirements` и `competencies → indicators`, хранится отдельно и имеет `is_synthetic=true`; реальные — `false`.

У каждого условия и индикатора `is_mandatory` — строго boolean; `false` обозначает желательное. `verification` — одно из `resume`, `documents`, `interview`, `test`. У групп и контекстных примечаний этих полей нет: они не самостоятельные проверки. `mandatory_basis` отдельно объясняет основание обязательности. Все 54 индикатора консультанта обязательные по решению команды, а не вследствие вычисления из процентов. Строка о праве знакомиться с документами по-прежнему `excluded_from_scoring=true` до содержательного решения; обязательность не снимает это исключение.

`origin=source` означает перенос содержания источника с `source_refs` (документ, SHA-256, адрес, дословная цитата). `origin=team` требует `rationale`: так помечены группировка IT и сформулированные командой строки. `interpretation_status=proposed` сохраняет факт, что конкретная интерпретация ещё ожидает ревью. Дополнения отделены полем `collection`; повторы не получают дополнительный вес автоматически. В `sources` каждого профиля перечислены документы с `source_id`, `role` и `revision`, связанными с манифестом. Редакция Python-ДИ — «1.2 от 01.02.2024»; неизвестные редакции — `null`, а не год из имени файла.

`check_stage` пока является дополнительным предложением для оценщика. Знания законов, английский и ПДн — индикаторы с `verification=interview`, вне формальных ворот. `verification=documents` допускает предварительное свидетельство по резюме, а окончательное подтверждение требует документа; это различие описано в `acceptance` и ещё требует согласования отображения. `evidence_channels` перечисляет возможные свидетельства, но не заменяет единственный способ проверки. Проценты консультанта — эталон источника, а не формула оценки: ДК сохраняет 100–100, остальные 90–100.

В вакансии PostgreSQL и ClickHouse перечислены в одной обязанности, а ClickHouse отдельно назван преимуществом. В `py.posting.05` предложено проверять PostgreSQL; ClickHouse остаётся желательным в `py.posting.11`, DataLens — в `py.posting.datalens`. Исходная общая цитата сохранена, разделение помечено `origin=team` и ожидает сверки Q-POSTING. Обязательность индикатора не превращает его в формальное условие допуска.

Параметры правил — предложение `schema_version=0.1`. Внутри образовательной альтернативы условия соединяются «и», между альтернативами — «или». Ключи альтернатив позволяют обсудить раздельные свидетельства. `requires_requirement` — предлагаемая зависимость требования направления от наличия высшего, пока не реализована оценщиком. Словарь `Education.level`, определения технического направления и старших курсов открыты; пустые списки примеров не отменяют ограничение.

Реальное требование Python по опыту не имеет численного порога и не добавляет обязательного коммерческого характера. Учебные 24 месяца находятся только в `synthetic/`. Неизвестный ключ или версия — ошибка обработки правила, без записи `formal_checks`; это не `unknown` кандидата.

## Совместимость

Базовая версия продукта `e2753c6`, контракт БД v1.0. **Полный пакет несовместим с текущей схемой для прямой загрузки**:

- У IT-компетенций `rank` и целевые проценты равны `null`, а БД v1 требует значения. Это сохраняет отсутствие данных, а не заменяет его фиктивным диапазоном.
- Построчное происхождение, этап/способ проверки, обязательность индикатора и результаты альтернатив пока не полностью представлены в БД.
- `key` — локальный идентификатор пакета, не UUID. Будущий загрузчик должен явно сопоставлять ключи с UUID и не переписывать старые версии профилей.
- Единый формат согласован по переданному сообщению Дениса. Функция загрузки и изменение схемы остаются за ним; отображение файлового пакета 0.2 на реализованную БД ещё не проверено. Отсутствие старого db-template-proposal.md больше не блокирует подготовку файлов.

До решения пакет предназначен для файловой сверки. Численные оценки, веса, агрегирование и утверждение профилей не выполнены. Открытые вопросы перечислены в `open_questions` с владельцем и зависимостью.

## Проверка

Из корня продукта, Python 3.13, без БД и сторонних зависимостей:

```powershell
python -m scripts.verify_requirement_profiles
python -m scripts.verify_requirement_profiles --archive "C:/path/to/Кадры.zip"
python -m unittest discover -s tests -p test_requirement_profiles.py -v
```

Проверка сопоставляет цитаты, адреса и хеши; проверяет полноту исходной матрицы, квалификаций и списка технических знаний Python, стабильные ключи, отдельную синтетику, диапазоны и границы цитат. С `--archive` дополнительно сверяет байты оригиналов и текстовые снимки с ZIP. Она **не оценивает кандидатов** и не доказывает семантическую правильность разметки или поведения модели.

При установленных зависимостях продукта можно также проверить объекты существующими Pydantic-схемами:

```powershell
python -m scripts.verify_requirement_profiles --card-schemas
```

Для каждого случая `case.evidence` содержит все цитаты кейса; где указаны `formal_evidence_indexes` и `indicator_evidence_indexes`, необходимо разделять основания. Цитата об API-тестах не является подтверждением длительности стажа. UUID в синтетике обозначают только версии учебных текстов.

Следующий шаг — сверка с Ильёй на ожидаемых случаях, с Денисом по отображению данных, решение о методике и назначение утверждающего. Текущая локальная проверка файлов не закрывает эти пункты приёмки.
