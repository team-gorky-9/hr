# Черновые профили требований

Два реальных профиля: консультант сектора подбора кадров (`hr-consultant`) и Python-разработчик (`python-dev`). Файловый формат `requirement-profile-review/0.2`, версия обоих профилей — **3**, статус `draft`. Рабочие рекомендации по черновикам не разрешены.

## Файлы и версии

- [profiles.draft.json](profiles.draft.json) — 4 формальных условия; у консультанта 5 компетенций и 54 индикатора (40 матрицы и 14 дополнений ДИ), у Python 8 предложенных групп и 53 индикатора. Всего 138 записей с учётом групп и примечаний.
- [sources.json](sources.json) — 4 документа, SHA-256, пути без `Кадры/` и текстовые абзацы. P — структурный абзац OOXML, L — строка TXT, это не номера страниц.
- [synthetic/cases.json](synthetic/cases.json) — отдельный учебный профиль и **25 ожидаемых случаев**, ревизия набора 2. Прежние 24 ID сохранены, добавлен `py-relevant-work-met`. Результаты модели здесь не записаны.

Загруженная Денисом v2 сохранена в истории продукта на `39260997bd11db41054bfb04544e382dcdf40181`. Новая v3 уточняет критерии направления образования и рабочего контекста опыта; ключи всех строк и source_refs сохранены. Существующую версию в БД не переписывают.

Исходники: [архив «Кадры.zip»](https://yadi.sk/d/hi1Jqc2lkE2tzw), SHA-256 `801efb82667a63d5d2370e6d39b00c74bea5069a3643472d41f476348a559baf`. Резюме кандидатов не включены. Текстовые снимки не подтверждают наличие подписей или актуальность правовых норм.

## Как читать строки

У каждого условия и индикатора boolean `is_mandatory` и один способ `verification=resume/documents/interview/test`. У групп и контекстных примечаний этих полей нет: они не самостоятельные проверки. `origin=source` означает перенос содержания с документом, хешем, адресом и точной цитатой; `origin=team` требует `rationale`. `interpretation_status=proposed` сохраняет факт, что конкретная интерпретация ожидает ревью. `mandatory_basis` отдельно объясняет обязательность.

Все индикаторы консультанта обязательные по решению Дениса. ДК сохраняет исходные 100–100, остальные — 90–100. Это не формула оценки и не перенос всех индикаторов в формальные ворота. Строка о праве знакомиться с документами остаётся `excluded_from_scoring=true` до содержательной сверки. У Python ранги/проценты null, конкретная группировка требует приёмки. `collection` отделяет исходную матрицу от дополнений; повторы не получают дополнительный вес автоматически.

У профиля `sources` содержит source_id, role и revision, связанные с манифестом. Python-ДИ — «1.2 от 01.02.2024», неизвестная редакция — null. Учебный профиль `is_synthetic=true`, реальные — false; учебные 24 месяца никогда не переносятся в реальный профиль.

Илья принял разделение PostgreSQL (`py.posting.05`) и желательного ClickHouse (`py.posting.11`), а также интервью по личным качествам и разделение обращений/ПДн. Общие исходные цитаты сохранены. Остальные содержательные вопросы остаются открытыми.

## Семантика правил после ревью Ильи

Форма `params` версии 0.1 принята с уточнениями ниже. Версия параметров отличается от версии файла 0.2 и профиля 3. Оценщик в этом пакете не реализован.

- Внутри альтернативы условия соединяются AND, между альтернативами OR. Хотя бы одна met → met; все not_met → not_met; иначе unknown. Ключи альтернатив сохраняют отдельные результаты и цитаты, хранение в БД ещё согласуется.
- Для `kind=education_level` допускается `field_group` внутри альтернативы, если источник задаёт уровень и направление одной фразой (Python-ДИ).
- `hr.education.field.requires_requirement` означает проверку направления по записям образования с подтверждённым нужным уровнем. Если уровень unknown, направление тоже unknown. Отказ по уровню автоматически не копируется в отказ по направлению: без независимых данных направление остаётся unknown, а общий итог уже учитывает отказ по уровню. Нельзя брать уровень одной записи и направление другой без связи между ними.
- Реальный опыт Python не имеет численного минимума и дополнительного ограничения «коммерческий». Для met нужен явный рабочий контекст. Допустимость стажировок и других видов опыта остаётся на содержательном согласовании. Описание проекта неизвестного характера не доказывает ни работу, ни отсутствие работы.
- Неизвестный ключ/версия: `processing_error`, `refusal_reason=rule_unsupported`, `write_formal_check=false`, `write_assessment=false`. Оценка по профилю не создаётся целиком; ошибка правила не становится unknown кандидата. Это ожидание для будущего оценщика, не реализация сохранения.

`check_stage` принят Ильёй: ворота резюме проверяют screening. Законы, английский и ПДн — индикаторы с verification=interview, вне этих ворот. При verification=documents предварительное met имеет basis=resume и подпись «по резюме, нужен документ». Илья предлагает после подтверждения документом новую версию оценки с basis=document. Столбцы basis/этапа и результаты альтернатив пока не согласованы в БД; нужно определить и основание test. `evidence_channels` перечисляет возможные свидетельства, но не заменяет verification.

## Карточки и доказательства примеров

`card_role=expected_available_fields` — ручное ожидание для полей существующего CandidateCard. Это не результат извлечения моделью и не полный контракт будущего экстрактора. Все 25 карточек содержат доступные сведения либо явно описанное отсутствие представимых фактов. Заглушек только с pii_hidden больше нет. Структурная валидность Pydantic не доказывает полноту извлечения.

`card_evidence` связывает заполненные фактические поля карточки (JSON pointer, например `/education/0/field`) с индексами цитат в case.evidence. Валидатор проверяет существование полей и ссылок, а не определяет семантическую правильность автоматически. `missing` — ручные ожидания о пробелах, не извлечённые положительные факты. `card_limitations` хранит факты, которые схема не выражает: статус и курс обучения, явное отрицание, тип и завершённость переподготовки. Они проверяются по исходному тексту.

В `hr-field-no` заполнено высшее по экономике. Пустой courses не доказывает отсутствие переподготовки: для not_met нужна цитата № 1. Это отмечено requires_text_evidence=true и formal_evidence_indexes=[0,1]. В `py-education-met` field=null, потому что специальность не названа; заявление о техническом образовании остаётся цитатой. Неизвестные названия работодателя, должности и даты не выдуманы.

Исторический ID `py-relevant-met` сохранён, но теперь результат unknown с вопросом о характере проекта. Новый `py-relevant-work-met` явно говорит «На работе в компании…» и ожидает met. Исторический суффикс met не определяет результат.

case.evidence — общий список цитат; formal_evidence_indexes и indicator_evidence_indexes разделяют основания. Цитата об API-тестах не подтверждает длительность стажа. alternative_evidence_indexes связывает отдельные исходы альтернатив с цитатами. Отрицание не выводится из пустого массива.

## Идентификаторы и нерешённые правила

Принят предложенный Ильёй namespace `d0137233-a161-59f2-876e-34ec1c1142a6`: `uuid5(UUID(uuid_namespace), text_key)`. Первые три текста используют его ключи `py-9001/text/base`, `py-9001/text/met-3y`, `py-9001/text/not-met-1y`. Остальные text_key содержат ID случая и версию. Изменённому тексту нужен новый версионный ключ; text_sha256 контролирует целостность. previous_candidate_text_id сохраняет соответствие прежним ссылкам. Это ID синтетики, не изменение UUID-политики БД. Переименование ключей профиля в наборе Ильи остаётся за ним.

Q-MONTHS открыт: прежние months=36 у overlap помечены months_status=pending_agreement, предложение Ильи — proposed_months=37 при включительных месяцах. Обе конвенции дают met для порога 24. Пока числа не являются утверждённым эталоном вычислителя. Трактовка противоречий при одинаковом исходе также остаётся предложением.

Словарь Education.level, статус обучения, Course.kind, определения технического направления и старших курсов ожидают решения. Пустые field_examples/exclusions не отменяют ограничения. Коды ОКСО из ответа Ильи не проверены и не приняты в данные. Предложения о счётчиках и same_as не превращены в алгоритм или новые поля БД; численные баллы не рассчитываются.

## Совместимость и приёмка

Старая схема v1.0 на e2753c6 несовместима с полным пакетом. Денис принял и загрузил v2 (3926099) в тестовую БД после миграции 0002. В hr/main на 09d32ef находятся загрузчик и контракт v1.1 (проект, ожидает утверждения Родиона). В текущую ветку профилей main не влит; схемы карточки в двух версиях совпадают.

Новая v3 проверяется отдельно: преобразование реальным build_profile из main и Pydantic-схемами выполняется без подключения к БД. Это не повторная загрузка в PostgreSQL и не подтверждение миграции на стенде.

В БД v1.1 пока не попадают check_stage, evidence_channels, mandatory_basis, interpretation_status, grouping_status, collection, issues, context_note, aggregation_method, признаки повторов/связей, verification_note и acceptance групп. Следующие изменения (basis, альтернативы, карточка, счётчики) согласуют Денис, Илья и Родион. Ключи строк пакета не UUID; загрузчик сопоставляет их с записями БД.

Илья вручную принял 20 из прежних 24 ожиданий и проверил цитаты. Модельного оценщика ещё нет; новые/исправленные случаи требуют повторной сверки. Реальные профили остаются draft, утверждающий не назначен.

## Проверка

Из корня hr, Python 3.13:

```powershell
python -m scripts.verify_requirement_profiles
python -m scripts.verify_requirement_profiles --archive "C:/path/to/Кадры.zip"
python -m unittest discover -s tests -p test_requirement_profiles.py -v
```

С зависимостями продукта:

```powershell
uv run --locked python -m scripts.verify_requirement_profiles --card-schemas
```

Проверяются ссылки/хеши/цитаты, полнота матрицы и квалификаций, реальные параметры без выдуманного стажа, карточки с объявленным назначением и доказательствами, ошибки всей оценки, границы цитат и правило UUID. С --archive сверяются реальные байты DOCX/TXT и извлечение абзацев. Эти проверки не заменяют содержательное ревью и прогон оценщика.

В штабе `tools/check_requirement_profile_handoff.py` проверяет сохранность ключей/источников относительно v2, три общих текста Ильи и преобразование v3 загрузчиком Дениса из зафиксированного Git-коммита. Скрипт читает уже полученные Git-объекты, работает во временном снимке кода, БД не подключает. Запуск из штаба: `hr/.venv/Scripts/python.exe tools/check_requirement_profile_handoff.py`.
