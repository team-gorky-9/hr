ID вопросов сохраняют связь с историей; status=resolved закрывает выбор правила, но не означает готовность реализации потребителя.

## Независимые контрольные примеры

Прежние [41 случай](synthetic/cases.json), учебный профиль v2 и ревизия 3 сохранены. Отдельный [content-cases.json](synthetic/content-cases.json) содержит **16 ручных ожиданий** для новых трактовок. Он не содержит карточек извлечения и не является входом загрузчика профилей.

Формат дополнения `requirement-content-cases/0.1`: версии двух реальных профилей, cases с целевым rule_key, этапом, basis, текстом и цитатами `[start,end)`. expected содержит result, included_in_screening и обоснование. `not_evaluated` означает исключённую строку или другой этап; это не unknown и не новый статус FormalCheckIn. `included_in_screening` описывает участие целевой строки на этапе резюме, не итог всего профиля. Формальные метки met/not_met/unknown для индикаторов соответствуют confirmed/contradicted/no_info потребителя. Положительный вывод по образованию с basis=resume предварительный по правилу v1.5.

Из корня продукта:

```powershell
uv run python -m scripts.verify_requirement_profiles --card-schemas --content-cases fixtures/requirement_profiles/synthetic/content-cases.json
uv run python -m unittest discover -s tests -p "test_requirement*.py" -v
```

CLI проверяет ссылки на ключи/версии, этапы, исключения и целостность цитат. Он **не вычисляет** семантический expected.result, не вызывает модель и не проверяет психологические качества. Интервью-примеры предназначены для будущего интервью-потребителя/ручной сверки; текущий оценщик резюме не должен оценивать их как screening.

## Зависимость оценщика: acceptance должно использоваться

В проверенной ветке Ильи c94285e `app/assessment/service.py::_assess_competency` передаёт модели только key и text; acceptance не включается. Поэтому принятый критерий ещё не гарантирует нужного поведения. Требуется передать критерии модели, проверить содержательную достаточность свидетельства и продолжать считать стаж/AND/OR/этапы/счётчики кодом. Для формальных альтернатив также должны доходить ограничения трактовки senior_student и technical; описание одного только названия условия недостаточно.

Контрольный пример: «Использовал SQL и PostgreSQL» не подтверждает весь перечень P110; он вообще не оценивается на screening. На интервью подтверждение только двух частей при непроверенных остальных даёт unknown по составной строке. Подмена acceptance общим промптом теряет это ограничение. Реализация и её проверка — у Ильи, не в данном пакете.

Денису остаётся хранение согласованного same_as; повторный загрузчик не создаётся. БД v1.5 и режимы после интеграции допускают техническую проверку учебного кандидата по явно выбранному неархивному draft. Реальный кандидат не переводится в technical ради обхода approve.

Файловая приёмка, проверка оценщика и рабочее утверждение — отдельные результаты. Для рабочего approve нужен реальный уполномоченный человек, конкретная версия и основание; эта правка их не подменяет.
