# Учебный набор первой волны

Все люди, организации, документы, основания и даты в наборе синтетические. Файлы служат общей базой для трёх независимо запускаемых сервисов по [контракту](../../docs/contracts/wave-1-common.md). Runtime подмен и проверки пишет каждый исполнитель в своей области.

| Файл | Назначение |
|---|---|
| actors.json | Логины ролей и пароль 123, UUID акторов, организация и scope. hr_other проверяет чужую область |
| organization.json | Учебные организации, подразделение и должность |
| selection.json | Положительный результат для начала оформления без ожидания готового подбора |
| job-description.txt | Источник требований для загрузки через API requirements |
| events.json | Три сообщения RabbitMQ с общей связью оформления и назначения |
| corrections.json | Исправленная дата и два альтернативных исхода отдельного запуска — corrected прежнего назначения или kept_existing с причиной |

ID примеров фиксированы для тестовых издателей/получателей. В реальном проходе ID, полученные из API, подставляются по смысловой связи; произвольная генерация нового ID при повторе того же сообщения меняет его смысл. В fixture actor пароль хранится явно как известное учебное значение.

## Общий интеграционный путь

1. В Workforce загрузить учебную организацию и акторов, войти hr/123. Получить тот же actor_id и область, которые использовались автономно.
2. В Requirements загрузить job-description, создать валидный черновик по requirement-draft/1.0, направить department, вернуть с замечанием, исправить, согласовать и утвердить. Подписчик получает requirements.approved, HTTP потребитель читает опубликованный профиль.
3. В Hiring создать дело из selection, запросить два учебных документа, один вернуть, получить исправление, подтвердить готовность и начало. Брокер доставляет employment.ready.
4. Workforce принимает intake. HR проверяет связь и регистрирует сотрудника/назначение. Публикуется assignment.registered с source_event_id, source_case_revision и correlation_id исходной передачи.
5. Hiring показывает кадровую ссылку и registered. Повторить события и команды, проверить прежние ID и отсутствие новых фактов.

## Матрица результатов

| Проверка | Ожидаемый результат |
|---|---|
| Неверный пароль | 401 без сессии |
| hr_other читает чужой объект | 404 без полей чужого дела |
| Тот же Idempotency-Key и та же команда | Прежний HTTP-результат и ID |
| Тот же ключ с изменённым телом | 409 IDEMPOTENCY_CONFLICT |
| Новая команда со старой expected_revision | 409 STALE_REVISION |
| Два принятых employment.ready с одним event_id | Один intake |
| Ответ assignment.registered на прежнюю версию оформления | Текущая версия не помечается зарегистрированной |
| Ошибка брокера после предметного commit | Данные сохранены, доставка pending, после восстановления доступен повтор |
| Остановка consumer после commit до ack | Повтор не создаёт второе назначение |
| Требование с неверной цитатой | 422 SOURCE_MISMATCH |
| Не принят обязательный документ | Готовность/начало отклоняются, предметный факт не меняется |
| Перезапуск сервиса | Файл, история и принятые данные доступны |

## Дополнительный проход исправления

После основного примера исходная дата назначения — 23 ноября. Исправленный employment.ready предлагает 24 ноября и переводит зарегистрированный intake в needs_review. В отдельном запуске HR выбирает apply_correction, получает тот же assignment_id с revision=2 и датой 24 ноября. В другом запуске HR выбирает keep_existing, назначение остаётся revision=1 с датой 23 ноября, сохраняется причина. В обоих случаях intake снова registered и публикуется assignment.review-resolved для исправленного event_id и case revision.

Hiring показывает registered для corrected и registered_with_difference для kept_existing. Проверить повтор команды, повтор сообщения, старую assignment revision, новую поправку во время просмотра, запоздалый ответ на прежний source_event_id и запрет повторного /register для существующего назначения. Смена person_ref, должности или подразделения не выполняется через apply_correction.

Workforce проходит матрицу с реквизитами и ссылками оснований. Загрузка/скачивание файлов относятся к Hiring и Requirements.

Команды запуска и фактические результаты своей поставки каждый автор фиксирует в README своего сервиса и продуктовом отчёте. Набор сам по себе не является работающим стендом.
