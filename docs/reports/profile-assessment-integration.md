# Проверка интеграции профилей и оценщика · 20.11.2026

Реализация находится в `feature/profile-assessment-integration`. База: main `fc61d26`, пакет `905ea9b`, ai-01 `c94285e`; локальные merge-коммиты `5448e1b` и `bc4e508` сохраняют историю коллег. Публикация и merge в main в этом шаге не выполнялись.

## Что изменилось

- Общая политика применимости hr-consultant используется до модели и при чтении API. Название чужой публикации не становится not_met. primary и comparison разделены, operational/technical сохраняют свои ограничения кандидата и профиля.
- Оценщик читает check_stage и acceptance, сохраняет предварительный met и отдельные альтернативы с цитатами, отклоняет неизвестные правила/ключи до модели. Полные даты YYYY-MM-DD принимаются с включительным подсчётом календарных месяцев; неполные даты сохраняют точность.
- Миграция 0005 хранит same_as, типизированные результаты индикаторов и групп, algorithm_version и calculation_as_of. Счётчики считает код, repository перепроверяет их и все вложенные цитаты. Подтверждение человеком создаёт новую версию с сохранёнными подробностями.
- API отделяет not_applicable/mapping_required от результатов требований; сравнение доступно явно. Показывает происхождение, подробные результаты, UTF-16 цитат и общие счётчики. Старый алгоритм даёт stale/algorithm_changed.
- Контекст и причины пропуска сохраняются отдельно от оценки пары. Повторная оценка не нужна при совпадении всех версий и as_of, но применимость пересчитывается. Вызов извлечения карточки не теряется из журнала при последующем сбое. Пакет без применимых записей не создаёт даже клиента модели.

Файлы профилей и прежние ожидания не переписаны: консультант v4, Python v5, учебный Python v2. Если эти версии уже загружены старым загрузчиком без same_as, он их не перезаписывает; требуется новая версия пакета при развёртывании, а не UPDATE существующего approved/draft.

## Воспроизведение

```bash
uv sync --locked
uv run python -m alembic upgrade head
uv run pytest
uv run python -m scripts.verify_requirement_profiles --archive <Кадры.zip>
uv run python -m scripts.verify_requirement_profiles --content-cases fixtures/requirement_profiles/synthetic/content-cases.json
uv run python -m scripts.replay_requirement_cases --mode controlled --output controlled.json
uv run python -m scripts.report_profile_applicability <Кадры-2.zip> --output coverage.json
```

Для полного pytest нужна отдельная TEST_DATABASE_URL с суффиксом `_test` и pgvector; pytest удаляет её схему. `alembic upgrade head` используют на предназначенной для разработки БД после проверки DATABASE_URL, не на произвольной рабочей базе.

[Отчёт 41 адресного прогона](requirement-cases-controlled-2026-11-20.json) содержит фиксированный hash эталона. Живой прогон: `uv run python -m scripts.replay_requirement_cases --mode live --output live.json` после настройки YANDEX_API_KEY и YANDEX_FOLDER_ID. Здесь эти настройки отсутствуют, живой запуск не выполнялся. Он проверяет формальное извлечение; полное качество карточки/профиля и содержательные интервью требуют отдельного замера. Ожидания в live-промпт не передаются.
