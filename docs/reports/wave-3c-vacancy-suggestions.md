## Что сделано

- `POST /api/v1/matching/suggestions` (201) и `GET /api/v1/matching/suggestions/{id}` — `app/matching/suggestions.py`.
- Таблица `matching_suggestions`, миграция `0011` (после `0010`, `alembic check` без расхождений с моделью).
- `run_search(..., read_only=False)`: поиск подборки идёт в той же транзакции, что и сохранение. Для `/search` и 3A по-прежнему используется снимок только для чтения.
- В снимке не хранится текст фрагмента. GET берёт его из действующего источника и не раскрывает заменённый или удалённый текст (`source_status`).

## Проверка

**Через HTTP.**
- Окружение: учебная база `hr_demo` (PostgreSQL 16, корпус `load-demo`), `alembic upgrade head` (0010 → 0011), `uvicorn app.main:app --port 8000`.
- Команда: `uv run python scripts/check_matching_suggestions.py`.

| Шаг | Результат |
|---|---|
| POST, вакансия `…00a1` ред. 1, «анализ и согласование требований к ИС», limit 3 | 201, автор `hr_demo`, `created_at`. Записи: search-9015, search-9001, search-9003 — все `available`, `not_evaluated`, с фрагментом |
| GET по id | 200, ответ совпадает с ответом POST |
| POST, ред. 2, «функциональные требования к СЭД» | 201, новый id, `vacancy_revision=2`, первой идёт search-9001 |
| GET первой подборки | не изменилась |
| Закрытая вакансия | 409 `VACANCY_NOT_PUBLISHED` |
| Роль department читает подборку | 403 `FORBIDDEN_ROLE` |

**Исправленный дефект.**
- Что было: на первом прогоне через HTTP ответ GET не совпал с ответом POST. Отличалась только запись `created_at`: в POST время было в UTC, в GET — в зоне сессии БД (МСК). Момент один и тот же.
- Исправление: после сохранения строка перечитывается (`session.refresh`), поэтому оба ответа берут одно сохранённое значение.
- Повтор именно этого случая: «совпадает с созданной: True».

**Тесты.** `uv run pytest tests/test_matching_suggestions.py` → 3 passed:
- создание, перечитывание и новая редакция (две подборки, первая не изменилась);
- откликов и записей резерва не прибавилось;
- текст кандидата заменён новой версией → `superseded` без фрагмента; кандидат удалён → `unavailable` без кода и фрагмента; в сохранённом снимке нет текста;
- отказы: department на POST и GET, неизвестный id (404 `SUGGESTION_NOT_FOUND`), закрытая вакансия, рабочий контур без ключа; отказы ничего не сохраняют.

Полный `uv run pytest` → **887 passed**, 0 пропусков.

## Для интерфейса

После публикации: `POST /api/v1/matching/suggestions` → показать `items` и запомнить `id`. Повторный показ — `GET /api/v1/matching/suggestions/{id}`. Записи с `source_status ≠ available` показывать без цитаты, с пометкой. Схема `SuggestionOut` — в `/openapi.json`.

## Ограничения

- Список подборок по вакансии (`GET ?vacancy_id=`) в контракте не задан и не сделан. `id` экран хранит сам.
- `applications` и `in_reserve` из поиска в снимок не сохраняются: это живые кадровые данные, их показывает карточка кандидата и поиск на момент просмотра.
- Сроки хранения и полный отзыв производных данных контракт оставляет общему механизму. Сейчас строки подборок не удаляются.
