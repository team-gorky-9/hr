# Единое окно взаимодействия · v1

**Дата:** 2026-11-21. **Статус:** серверная реализация v1; [запуск и точные HTTP-формы](../modules/interaction-window.md), [границы проверки](../reports/interaction-window.md). **Ответственный за серверную поставку:** Давид. **Потребители:** интерфейс Аси, макеты Маши, владельцы Hiring и legacy workflow.

## Граница и размещение

В runtime Hiring размещается модуль объединения разрешённого чтения двух источников: candidate-portal и legacy workflow. Источники остаются владельцами состояния, прав, истории и команд. Отдельной общей БД ожиданий и универсальной команды «завершить взаимодействие» нет. RabbitMQ для этого чтения не требуется. Существующие [операции кандидата](wave-5-candidate-portal-stage-1.md) и [workflow](workflow.md) сохраняются; для новых запросов сведений addendum требует возвращённый Q-ref.

Первая поставка ограничена учебной организацией и контуром training. Legacy-экземпляр явно закреплён за одной организацией: его contour не заменяет tenant. Многоорганизационная изоляция и полноценный рабочий вход не считаются готовыми.

## Вход и доступ

Проверенный сервером актор определяется issuer, actor_id, organization_id и разрешённым контуром. Серверный mapping связывает его с конкретными legacy instance/User и версией соответствия. Совпадение login, имени или email не устанавливает личность. Нет mapping, несколько соответствий, неактивный User, другая организация — доступ к источнику закрыт. Кандидату legacy mapping не предоставляется.

Входные actor_id и X-User-Login не определяют исполнителя. Серверный адаптер удаляет служебные identity-заголовки клиента, сам выбирает разрешённый legacy login и вызывает только фиксированные маршруты. Legacy listener закрыт от браузера и внешней сети; пока обходной вход открыт, общее окно не включается. Fixture/123 используются только как явно учебный вход, без заявления защиты реальных учётных записей.

Источник проверяет право перед выдачей каждой строки, детали и каждой командой. Список не расширяет область доступа. Нет общего кеша частных ответов; при выходе/смене роли и отказе доступа клиент удаляет прежнее содержание. Недоступность проверки права не разрешает показывать старую закрытую строку.

## Чтение

`GET /api/v1/interaction-window` — новая операция композиции. Вход: `relation` (needs_my_action/waiting_on_other/completed/information), необязательный типизированный `subject_ref`, cursors отдельных источников. Свободный текстовый поиск и массовые команды не входят в v1. Фокус требует source/kind/id; неоднозначное описание ведёт к выбору записи, не к команде.

Ответ содержит `schema_version=1`, `generated_at`, `completeness` (complete/partial/unavailable), `sources[]` и `items[]`:

| Поле | Состав и смысл |
|---|---|
| sources[] | source; status=ok/unavailable/not_linked/not_applicable; observed_at; source_as_of или null; next_cursor или null; coverage=complete/page/unknown; безопасный error_code |
| items[].key | source + organization/instance + contour + kind + subject_id + expectation_ref; ключи R1 и A1 не объединяются |
| subject_ref / related_ref | Тип/ID дела. Связь R1↔A1 видит только уполномоченный HR после ручного подтверждения; кандидат не получает legacy ref |
| expectation_ref | Уточнение: request_id/event_sequence; передача: attempt_id; разбор: attempt_id/feedback_id/revision |
| relation / state / reason_code | Мой ход, ожидание, завершение или информация; конкретное предметное основание |
| responsible | self, разрешённый actor ref, role_scope либо external; без назначения HR указывается очередь организации |
| title / next_step / due_on | Шаблонный текст без контактов, свободных сообщений и резюме; срок из источника либо null |
| basis_ref / source_version | Разрешённое основание и типизированные версии: request_revision/sequence; attempt/feedback revision/stage seq/review ref/assignment revision. Не глобальный счётчик |
| occurred_at / observed_at | Время предметного события либо null; время получения сервером. Формат `2026-11-21T14:30:00+03:00` |
| actions[] | code, target={source,kind,id}, required_version, availability и причина недоступности; подсказка интерфейсу, не полномочие |

Источники возвращают узкие разрешённые страницы; полный старый GET с последующим обрезанием не заменяет source-side pagination. Cursor непрозрачен, связан с источником, актором, областью, фильтром и порядком. Начальный UI показывает секции источников; общего total и атомарного снимка нет. Порядок задаёт источник с устойчивым ID для равных значений. После команды или изменения прав список начинается заново. До пагинации допустим только явно ограниченный fixture-набор.

Чтения идут параллельно с ограниченными connect/read/overall deadlines и размером ответа. Параметры задаются по короткому замеру учебного пути и бюджету UI; произвольные значения этим контрактом не назначаются. Неприменимый источник не запрашивается. Есть доступная часть → 200 partial; все применимые источники недоступны → 503; неверная общая сессия → 401. Not-linked не равен нулю дел. Пустой список означает отсутствие дел только при ok/complete. Старые чувствительные строки при неудачном обновлении убираются, время последнего успеха может остаться без содержания.

## Предметные расширения

### Уточнение кандидата

Hiring выдаёт `information_request_ref={request_id,event_sequence}` своего события information.requested. Дополнение принимает эту ссылку вместе с expected_revision и проверяет, что запрос текущий. Обновление revision после загрузки файла не позволяет ответить на заменённый Q1 вместо Q2. Текущий запрос заменяется новым, история сохраняется. Ключ строится из события источника, не timestamp. Неоднозначная старая корреляция получает basis_unknown.

Read сообщения сохраняет первую read_at; не завершает запрос, не меняет кадровый статус. HR видит факт прочтения кандидатом, а не собственный счётчик непрочитанных. Сырая история событий не используется как кандидатский DTO: только белый список полей источника.

### Рассмотрение отзыва

Legacy добавляет FeedbackReview: id, application_id, точные `{attempt_id,feedback_id,revision}`, reviewer_user_id, created_at, basis, request_id, результат stage_changed со StageEvent либо continue_waiting с проверенной seq. Разрешён только HR/admin своего контекста. Несколько учтённых отзывов допустимы у одного явно выбранного A1; команды по фильтру запрещены.

Источник атомарно проверяет актуальные версии отзывов и expected_seq, сохраняет review и, если выбран переход, StageEvent. Дубликат request_id с тем же телом возвращает прежний результат; другое тело — 409 REQUEST_ID_REUSED. Новая версия отзыва требует нового review, не отменяет прежнее кадровое решение. Исторические ответы без review помечаются «разбор не подтверждён», а не «никто не рассматривал».

### Отзыв назначения

HandoffAttempt получает assignment_revision, access_revoked_at/by/reason; recipient и снимок сохраняются. HR отзывает назначение на точную попытку с expected_assignment_revision и request_id. Другая версия → 409; повтор того же запроса не создаёт новое событие. Новому получателю создаётся новая попытка, исходная история не переписывается.

Отзыв и ответ сериализуются на попытке: после отзыва новый ответ прежнего получателя запрещён. Все пути списка/детали/сводки/feedback проверяют активное назначение; Application/CandidateText доступны по объединению активных разрешённых попыток. Отзыв H1 не закрывает независимые права H2 и не раскрывает H1 через историю другого дела. Сам отзыв доступа не закрывает предметное ожидание; HR видит необходимость отдельного решения. Старые закрытые попытки не объявляются отозванными при миграции.

## Команды и ошибки

Окно выдаёт фиксированные действия перехода к форме владельца, не произвольный URL/proxy. Предметные тела и ограничения остаются у источника: expected_revision у R1, expected_seq у этапа, supersedes_id у исправления feedback, request_id у повторяемой команды. Устаревшая форма → 409 без автоматического обновления версии и повторной отправки. После потерянного ответа POST перечитывается результат; новый request_id автоматически не создаётся.

Hiring возвращает 404 для чужого/неизвестного дела; legacy department сохраняет нейтральный 403 FORBIDDEN_SCOPE. Недопустимые состояние/переход/адресат остаются предметной ошибкой. Прочтение сообщения не считается ответом; ответ не считается кадровым решением.

## Два обязательных примера

1. HR запрашивает Q1 по R1. C1 получает «Дополнить», HR — «Жду кандидата»; C2 не получает строку R1. Read M1 не закрывает Q1. Дополнение C1 с актуальными Q-ref/revision создаёт submitted и новую версию: HR видит «Проверить дополнение», C1 — ожидание HR. HR ставит ready с основанием, затем вручную подтверждает связь с существующим A1; автоматической склейки по имени нет.
2. HR создаёт H1 для D1 со снимком и сроком, затем независимую H2. D1 отвечает именно H1, fit/not_fit закрывает H1; H2 остаётся открытой, этап A1 не меняется. HR отдельно записывает review и выбирает ждать H2 либо изменить этап. Явная смена этапа по действующему workflow может закрыть H2 с причиной stage_moved; это не ответ D2. Поздняя правка H1 не снимает H2. HR отдельно публикует разрешённый исход R1; кандидат не получает внутренний отзыв. При отзыве назначения H1 D1 не открывает старую ссылку, независимая H2 остаётся доступной.

Employee-feedback проверяет границу общего представления: именное обращение видно автору/назначенному адресату, мера — разрешённой аудитории. Первичный анонимный ответ, код участия и вывод о личности ответившего никогда не образуют персональную задачу. Подключение этого третьего адаптера не входит в первую поставку.

## Поставка и обратимость

Добавляются модуль композиции Hiring, узкие source read-операции, Q-ref, FeedbackReview, отзыв назначения и серверный mapping. Старые API сохраняются; история не удаляется; недоказанные старые связи не восстанавливаются по времени. Отключение окна возвращает прежние экраны без удаления ответов/решений.

Проверка будущей реализации: один короткий HTTP-проход двух случаев с перечитыванием; две отрицательные группы — чужой/отозванный доступ и старая форма/поздний H1 при открытой H2. Частичный отказ проверяется подменой одного адаптера без брокера. UI, рабочая identity, большие базы и многоорганизационная изоляция не объявляются проверенными по этому сценарию.
