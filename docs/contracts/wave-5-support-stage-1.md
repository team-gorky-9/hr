# Волна 5 · социальная поддержка · этап 1

Четыре небольших задачи Дениса. Собственный social-support пакет и /api/v1/support, локальные файлы и обычное постоянное хранение. Для самостоятельного пути нужны учебные правила и назначенные акторы. Внешний бухгалтерский сервис, OCR, модель и брокер не требуются.

## Основа и доступ

RuleVersion = {id,support_type,title,required_items:[{key,title}],source_reference,is_synthetic,status:draft|published}. На демонстрации используется явно учебный вид помощи; список приложений не выдаётся за действующий нормативный перечень.

Case содержит id,organization_id,applicant_actor_id,rule_version_id,revision,status:draft|submitted|needs_information|ready_for_review|decision_recorded|withdrawn|closed,assigned_specialist_id:null|UUID,assigned_secretary_id:null|UUID. Контактные/содержательные поля собственной подачи видит заявитель. Специалист и секретарь получают доступ по отдельному назначению на дело. Совпадение роли и организации само по себе не открывает все материалы.

Общие UUID/даты/revision. Команды изменения имеют expected_revision; чужой объект — 404, неверное состояние — 409, ошибки данных — 422. Автор действия и автор внешнего решения хранятся раздельно. Публичное объяснение заявителю отделено от служебной записи.

## 5A · черновик и подача

| Операция | Результат |
|---|---|
| GET /rules | Доступные опубликованные версии учебных условий |
| POST /cases {rule_version_id,statement} | Собственный draft заявителя |
| PATCH /cases/{id} {expected_revision,statement} | Заявитель редактирует свой черновик |
| POST /cases/{id}/documents | multipart file,item_key → неизменяемый Document |
| GET /cases/{id} | Собственная карточка/комплект; служебная видимость по назначению |
| GET /cases/{id}/documents/{document_id}/content | Разрешённый оригинал, проверка дела и вида документа |
| POST /cases/{id}/submit {expected_revision} | Фиксирует снимок подачи/версии приложений, submitted и время |
| GET /cases | Свои дела заявителя; назначенные дела специалиста; минимальная очередь распределения у координатора |

Document хранит UUID, case_id, item_key, original_name, content_type, size_bytes, sha256, uploaded_by, created_at, visibility:applicant|internal. Файлы локальны, путь создаёт сервер, original_name не становится путём. Сбой загрузки не оставляет документ с ложным «принят». Рестарт не стирает оригинал. Для заявителя разрешены только его applicant-документы и персональная выписка.

Координатор читает в очереди номер, вид помощи, дату, applicant_ref и статус для назначения, а не автоматически всё заявление/приложения. POST /cases/{id}/assign {expected_revision,specialist_actor_id,secretary_actor_id,assignment_basis} назначает участников своей области. Конкретные назначающие в рабочей организации ещё требуют подтверждения; в примере они заданы fixture.

Демо — draft, два файла, подача, номер и зафиксированный состав. Другой сотрудник не открывает дело или файл по ID. Доступ HR к личному черновику не возникает автоматически.

## 5B · комплектность и дополнения

ChecklistResult = {id,case_id,submission_revision,items:[{key,result:present|missing|unreadable|needs_clarification,document_id:null|UUID,reason}],reviewed_by,reviewed_at}. Назначенный специалист проверяет конкретные версии.

В Case отдельно сохраняется staff_confirmation {state:confirmed|unknown,source_reference,verified_by_actor_id,verified_at}. Назначенный специалист регистрирует его через POST /cases/{id}/staff-confirmation {expected_revision,state,source_reference}. Роль employee сама по себе не объявляется проверкой реальной занятости. Для учебного пути можно подтвердить явно синтетический кадровый источник.

POST /cases/{id}/completeness {expected_revision,items,public_message} сохраняет проверку. Неполнота даёт needs_information, полный комплект и confirmed кадровое основание — ready_for_review. При неизвестном статусе специалист видит отдельный вопрос проверки. Наличие файла означает только его наличие, а не подлинность или право на помощь.

POST /cases/{id}/addenda {expected_revision,text,document_ids} выполняет заявитель в ответ на запрос. Приложения загружены в его дело, создаётся новая версия поданных материалов. Прежние документы и результат проверки остаются в истории. GET /cases/{id}/history показывает допустимые роли события и объяснения.

Демо — специалист возвращает нечитаемый файл, заявитель добавляет новый, специалист подтверждает комплектность новой редакции. Запоздалое подтверждение старой revision не закрывает новый запрос.

## 5C · решение и персональная выписка

POST /cases/{id}/decision {expected_revision,outcome:approved|declined|needs_information,public_explanation,source_reference,source_author,decided_on,recording_basis} выполняет назначенный секретарь. Источник — внешнее решение уполномоченного рассмотрения; его состав и порядок не выдумываются в API. approved/declined требуют ready_for_review, возвращение за дополнением даёт needs_information. Запись хранит автора исходного решения и регистратора отдельно.

При approved/declined дело получает decision_recorded. Для заявителя формируется собственная выписка из результата, даты, допустимых реквизитов и public_explanation. GET /cases/{id}/extract отдаёт её как текст/JSON с версией. Вложенный внутренний протокол и дела других заявителей в неё не входят.

В первой поставке предусмотрена регистрация внешнего решения, а не цифровое голосование комиссии. Секретарь, являющийся заявителем, не регистрирует своё решение; координатор назначает другого. Исправление зарегистрированного решения — новая запись POST /cases/{id}/decision-corrections с теми же полями, expected_revision и обязательным correction_reason; прежняя редакция сохраняется и персональная выписка получает новую версию.

Демо — подтверждённый комплект → внешнее решение → собственная выписка. Во втором случае declined с понятным объяснением. Другой заявитель и обычный руководитель не читают внутреннее основание.

## 5D · исполнение и закрытие

ExecutionRecord = {id,case_id,status:confirmed|failed|unknown,source_reference,source_author,occurred_on:null|date,note,recorded_by,recorded_at}. POST /cases/{id}/execution {expected_revision,status,source_reference,source_author,occurred_on,note} доступен отдельно назначенному исполнителю/регистратору своей области, только после approved. Назначение исполнителя добавляется координатором к делу с основанием.

Подтверждённое исполнение и неизвестность — разные состояния. Суммы/банковские реквизиты не требуются первому учебному пути. Если они появятся в реальной процедуре, состав и доступ задаются отдельно. GET /cases/{id} показывает заявителю разрешённый результат исполнения.

POST /cases/{id}/close {expected_revision,reason} завершает дело уполномоченный специалист. При одобрении и неизвестном исполнении требуется явное основание организационного закрытия; экран сохраняет unknown, а не изображает выплату. При declined достаточно зарегистрированного решения. POST /cases/{id}/withdraw {expected_revision,reason} позволяет заявителю отозвать дело до записанного решения. После решения последствия отзыва рассматриваются владельцем процесса, автоматического удаления нет.

Демо — approved, затем неизвестное исполнение, затем подтверждение по внешнему источнику и закрытие. Во втором примере отказ виден без обещания выплаты. Ни загрузка документа, ни решение комиссии сами по себе не означают исполнение.
