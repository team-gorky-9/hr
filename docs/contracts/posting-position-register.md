# Публикация → должность → профиль

Версия контракта `posting-register/1.0`, 20.11.2026, requirements-03. Полную техническую задачу Давид принял от Родиона. Это реализованный контракт ветки; предметное утверждение HR и согласование отсутствующими коллегами не подразумеваются. Предыдущий [проект формата](posting-position-register-proposal.md) остаётся историческим пакетом оснований, runtime читает формат ниже.

## Область и решения

`app.postings.registry` читает `app/postings/data/current.json` → `versions/<version>.json`. `POSTING_REGISTRY_DIR` задаёт другой каталог. Поставляемая версия — `v1`; после публикации файл версии не редактируют. Новое решение добавляют отдельной версией и переключают указатель. Версия в имени обязана совпадать с содержимым; переходы путей, неизвестные поля, дубли нормализованного ключа и неполные решения запрещены. Приложение читает текущую версию заново, не держит устаревающий глобальный кэш.

Ключ правила: `dataset_id`, автоматически вычисленный `dataset_sha256`, `channel`, `source_folder`, `is_synthetic`, `match_kind` и исходное `posting_title`. Названия сопоставляются только через NFC, casefold и свёртку пробелов. Идентификаторы контекста сохраняются точно; одинаковое название в другом наборе не наследует решение. Fuzzy matching и вывод должности из слова «консультант» отсутствуют.

| decision_state | Содержание |
|---|---|
| `confirmed` | Одна существующая целевая должность `position_code`; автор, дата, основание и ссылки обязательны |
| `needs_review` | Цель и метаданные отсутствующего решения пусты; есть причина и источники вопроса |
| `no_matching_position` | Владелец явно подтвердил отсутствие подходящей должности в каталоге; автор, дата, основание и ссылки обязательны; цели нет |

`excluded_position_codes` — отдельное отрицательное свидетельство о конкретной паре. Два реальных названия исключают `hr-consultant`, но остаются `needs_review`: это не отсутствие любой подходящей должности. Реальные семь HR-правил не подтверждены. Пять IT-правил основаны на конкретной папке, публикации и ДИ. Два подтверждения учебного набора ограничены `is_synthetic=true`. [Источники и ограничения ДИ](posting-registry-sources.md).

## Происхождение импорта

Миграция `0007_posting_sources` после `0006` добавляет `application_posting_sources`: UUID, FK `application_id`, набор и fingerprint, канал, путь, папка, SHA исходных байтов, дата. Уникальность: отклик + набор + fingerprint + канал + путь + SHA. UPDATE запрещён триггером; повторное наблюдение не дублируется. Удаление отклика каскадно удаляет его происхождение. Это не новая запись отклика.

`mapping.json` принимает необязательный непустой `dataset_id`. Fingerprint версии 1 — SHA-256 UTF-8 JSON массива `{source_path,sha256}`, отсортированного по NFC-пути со слешами `/`, затем по SHA (null сортируется как пустая строка). JSON: `ensure_ascii=False`, `sort_keys=True`, разделители `,` и `:`. Включаются **все** входы `read_package`, в том числе исключённые, неподдерживаемые и ошибки; отсутствие байтов обозначается null. Текст распознавания в хэш не входит. Пользователь не передаёт доверенный fingerprint через mapping.

Происхождение записывается внутри savepoint успешного импорта RESPONSE: новый кандидат, дополнительный отклик, повтор. Те же байты в другой папке получают происхождение второго отклика, а не первого SourceDocument. История не получает primary-контекст. Старые данные без происхождения возвращают `missing_context`; миграция его не угадывает. Повторный импорт проверенного полного пакета добавляет недостающие свидетельства без новых откликов. Новый отличающийся контекст того же отклика сохраняется; несколько контекстов дают `ambiguous_context` до сверки.

Для `fixtures/kadry_mapping.json` вход — именно распакованный корень **Кадры**, не его родитель. `__MACOSX` и скрытые файлы исключаются штатным чтением; архивный ZIP-хэш и fingerprint входов различны. Добавление файлов в пакет меняет fingerprint и требует новой проверенной версии правил. Для выгрузки parser corpus действуют фактические записи `read_package`, а не предположение об идентичности ZIP.

## Выбор и запуск

`resolve_application` проходит `Application(source=response)` → отдельные источники отклика → правило реестра → `Position` → `repo.get_approved_profile(... synthetic=candidate.is_synthetic)`. Импортированные vacancy, title, stage и history не переписываются; вакансии и должности не создаются. UUID и номер профиля доступны до первой оценки.

В результате `ApplicationResolution`: `application_id`, `candidate_id`, `is_training`, `mapping` с версией/хэшем реестра и входа, исходным названием, решением, основанием и объяснением; `position_id/code`, `profile_id/version`, `ready`, `reason`. Причины различают `missing_posting`, `missing_context`, `ambiguous_context`, `contour_mismatch`, `unknown_publication`, `ambiguous_mapping`, `awaiting_hr`, `no_matching_position`, `position_not_found`, `no_approved_profile`, `not_response`, `ready`. Список контекстов не содержит имени файла или текста резюме.

Пустое название разрешается только явным правилом `folder` данного набора. Непустое несовпадающее название не наследует разрешение папки. Правило смешанной реальной HR-папки не существует. Один контекст с двумя подходящими правилами остаётся неоднозначным.

`assess_in_context` для primary больше не требует заранее выбранного профиля. Переданный `profile_id` — ограничение: он обязан совпасть с разрешённым approved-профилем. Отсутствующая связь/профиль даёт audited `skipped` без настройки и вызова модели. При смене решения кэш оценки не обходит проверку. Манифест `assessment_run` v1.1 хранит полную версию реестра, разрешение, выбранные UUID/версии и существующие параметры оценки. Старый аргумент `policy` отклоняется: глобальная таблица заголовков не заменяет scoped registry.

Явный `purpose=comparison` сохраняет расчёт пары и ограничения режима, не меняет исходный отклик. Учебное прямое сравнение с неархивным рабочим draft остаётся допустимым прежним контрактом. Cross batch выбирает пары только из текущих approved-профилей контура, определяет primary по разрешённым RESPONSE, проверяет актуальность выбора перед использованием кэша. Неоднозначный исходный отклик может участвовать в comparison только по явному запуску `--all-approved`.

## HTTP и совместимость

Список/карточка отклика добавляют `posting_resolution`; `target_position_code` означает подтверждённую цель и может быть null. `vacancy` сохраняет импортированную вакансию. Оценка читается по профилю разрешённой цели. Без связи — `mapping_required`, при явном отсутствии должности или исключении импортированной пары — `not_applicable`, при отсутствии approved — `no_approved_profile`. Последнее не отменяет подтверждённое соответствие публикации.

Старое поле `applicability` и его четыре счётчика остаются адаптером: confirmed / mismatch / unresolved / not_covered. Новое `no_matching_position` нельзя выводить обратно из legacy mismatch. Списки откликов и их количества ограничены `source=response`; воронка уже имела это ограничение. Cross показывает признак исходной должности по реестру, а отметку отклика на конкретную вакансию — по сохранённому RESPONSE.

Ответ comparison тоже содержит `posting_resolution` исходного отклика. Его `target_position_code` остаётся явно выбранной целью повторного рассмотрения. Если подтверждённая исходная должность отличается, legacy applicability возвращает `mismatch/different_target`; оно больше не вычисляется из глобального списка одинаковых названий.

| Маршрут | Поведение |
|---|---|
| GET `/api/v1/applications/{id}/posting-resolution` | Разрешение без оценки, как чтение карточки; неизвестный ID — 404 |
| POST `/api/v1/posting-snapshots` | `{application_ids:[UUID,...]}` (1–5000), HR/admin через существующий `X-User-Login`; сохраняет снимок, 201 |
| GET `/api/v1/posting-snapshots/{id}` | HR/admin, возвращает сохранённый снимок; неизвестный ID — 404 |

## Снимок T-13

`posting-snapshot/1.0` записывается через append-only AuditLog. В нём полное содержимое/хэш реестра, уникальные ID выбранных RESPONSE, исходная публикация/вакансия, доказательства происхождения (путь заменён SHA), контур, разрешение и UUID/версии профиля, текста и сохранённой оценки при наличии. Отдельно: `response_count`, `candidate_record_count` (не число уникальных людей), `decision_counts` всех трёх состояний, `ready_count`, `blocked_count`, `reason_counts`. Повтор ID в запросе не увеличивает знаменатель; история/manual/reserve отклоняются.

SHA снимка проверяется при чтении. Чтение не обращается к текущему реестру/профилю/модели и потому воспроизводит исходный отбор после отзыва решения, замены approved-профиля или исчезновения current.json. Это воспроизведение сохранённого среза, не повтор стохастического расчёта LLM. Новый пересчёт создаёт новый снимок. Число откликов и их этапы не меняются.

## Команды и проверка

```powershell
uv run alembic upgrade head
uv run python -m app.ingest --input fixtures/stage_0a --mapping fixtures/stage_0a/mapping.json
uv run python -m app.postings resolve --application-id <UUID_RESPONSE>
uv run python -m app.postings snapshot --application-id <UUID_RESPONSE>
uv run python -m app.postings read-snapshot --snapshot-id <UUID_SNAPSHOT>
uv run python -m app.postings --registry-version v1 resolve --application-id <UUID_RESPONSE>
uv run python -m app.assessment run --candidate-code py-9001 --application-id <UUID_RESPONSE> --technical
```

Для последней команды нужен утверждённый **учебный** профиль, [загрузка](../modules/requirements.md). Модель настраивается существующим способом. `run --position-code` — необязательное ограничение ожидаемой цели. В обычном `batch --position-code` параметр сохраняет смысл фильтра импортированных вакансий: каждый выбранный RESPONSE разрешается отдельно, нерешённые попадают в отчёт skipped. В `batch --all-approved --position-code` фильтр относится к разрешённой исходной должности. Comparison требует явный `--position-code`.

Проверки: `uv run pytest` на отдельной PostgreSQL с pgvector и `TEST_DATABASE_URL` с суффиксом `_test`; pure `tests/test_posting_registry.py` доступен без БД. [Реальный агрегат](../reports/requirements-03-posting-mapping.json) содержит 287 DOCX и результат runtime resolver без ПДн. [CLI/миграции/HTTP](../reports/requirements-03-integration.json) — отдельный синтетический прогон. Поставка проверена из checkout; wheel-сборка в проекте не настроена (`tool.uv.package=false`). В этом репозитории нет frontend-приложения: проверены HTTP DTO, не браузерная вёрстка потребителя.
