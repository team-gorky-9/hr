# Requirements и Hiring · этап 1 функциональной поставки

Решение Родиона от 21 ноября 2026. Этот документ имеет приоритет над инфраструктурными требованиями wave-1-common, wave-1-requirements и wave-1-hiring **для сдачи этапа 1 Дениса и Ильи**. Давид завершает почти готовый Workforce в прежнем объёме; его контракт этой редакцией не изменён. Уже реализованная инфраструктура сохраняется.

Этап 1 даёт работающие HTTP-операции, постоянные данные и понятные состояния для подключения интерфейса. Этап 2 добавляет принятую сервисную архитектуру и надёжный автоматический обмен. Бизнес-поля, видимость и ошибки исходных контрактов применяются в пределах включённых ниже операций.

## Что требуется сейчас

- FastAPI/OpenAPI, действующие роли и области, проверка входов, сохранение данных и необходимая история изменений.
- Hiring и Requirements могут независимо использовать AUTH_MODE=fixture из common и общий набор actors. Вход hr/123 обеспечивает Workforce Давида при подключении. Ожидание этого подключения не блокирует автономную сдачу.
- Постоянное хранилище данных в уже принятом окружении. Автор сохраняет выбранную и уже работающую структуру. Отдельные контейнеры, собственный брокер и универсальный launcher не являются условием сдачи этапа 1.
- Документированная команда запуска и короткий воспроизводимый проход через HTTP. Бизнес-проверки, чужая организация/чужое дело, ошибочный вход, сохранение после рестарта.
- expected_revision на изменении сохраняется, чтобы устаревшая форма не перезаписала исправление. Создание дела по тому же application_ref и повторное утверждение той же редакции не создают дубля. Полный общий движок replay Idempotency-Key переносится в этап 2; в этапе 1 заголовок допускается, но его общий replay не заявляется, если не реализован.

В /health указать implementation_stage=1, integration_mode=standalone, auth_mode. Hiring дополнительно возвращает transfer_mode=manual. Успешная выдача своего результата не зависит от доступности соседнего сервиса или RabbitMQ.

## Requirements · Денис

Сейчас реализуются должности, загрузка источников, создание/редактирование черновика, назначение согласующего, возврат и исправление, утверждение, новая редакция и чтение прежнего/текущего профиля, история и документы по wave-1-requirements. Формат requirement-draft/1.0, проверка цитат и право утверждения сохраняются.

Полный путь проходит через HTTP на учебной ДИ. Согласующий получает выбранный черновик, возвращает замечание, автор исправляет, согласующий принимает, HR утверждает точную редакцию. После публикации v2 профиль v1 читается по прежнему ID, current указывает v2. Один current обеспечивается обычной транзакцией и ограничениями БД. Готовый профиль доступен через GET, публикация не ждёт брокера.

Для файлов сохраняются оригинал и ссылка на редакцию извлечённого/введённого текста. Текстовый PDF/DOCX/TXT используют доступное извлечение; непригодный источник имеет понятную причину и предусмотренный ручной ввод с основанием. Вызов внешней модели не требуется для этого результата.

В этап 2 относятся requirements.approved через RabbitMQ, outbox/inbox, publisher confirms, повторы доставки, dead-letter, /deliveries, автоматическое обновление потребителей и распределённая матрица сбоев. Уже написанный код этих механизмов можно сохранить, отключив обязательную зависимость запуска от брокера.

## Hiring · Илья

Сейчас реализуются дела, список/чтение, связь с кандидатом, комплект, запрос, загрузка документа, возврат/исправление, проверка готовности, подтверждение начала, отзыв до начала, локальное исправление начала и история по wave-1-hiring. Данные и оригиналы файлов сохраняются. Кандидат видит свою разрешённую часть; документы другого дела не открываются.

Вход — selection.json или явное подтверждённое HR решение с source_mode. Формальная интеграция с исходным подбором не требуется для первого учебного прохода. Полный цикл комплекта реально выполняется по API.

POST /cases/{id}/start сохраняет подтверждённый факт в Hiring и возвращает его без ожидания Workforce. workforce_status=not_sent означает «кадровая запись ещё не подтверждена», transfer_mode=manual. UI не получает обещания автоматической передачи. HR читает реквизиты из GET /cases/{id} и регистрирует сотрудника/назначение в Workforce либо во внешнем кадровом источнике.

Для завершённого ручного пути добавить POST /cases/{id}/record-assignment с телом {expected_revision,employee_ref:{system,id},assignment_ref:{system,id},actual_starts_on,confirmation_basis}. id — UUID, system — workforce или external. hr/admin своей организации записывает подтверждение и источник. Сервер хранит автора и дату регистрации, помечает способ manual-confirmed. Это подтверждение HR, автоматической проверки соседнего сервиса не заявляется.

Ответ — Case с workforce_status=registered при совпавшей дате либо registered_with_difference при иной actual_starts_on. Хранятся workforce_assignment_snapshot и объяснение. Предметный статус остаётся started. Повторная ручная запись допускается только с новой ревизией, основанием и сохранением истории. Состояние до started даёт INVALID_STATE.

Case дополнительно возвращает transfer_mode="manual", workforce_confirmation {employee_ref,assignment_ref,actual_starts_on,confirmation_basis,recorded_by_actor_id,recorded_at} либо null. В snapshot сохраняются фактическая дата и источник. Старые employee_id/assignment_id заполняются для system=workforce, для external остаются null, чтобы разные пространства ID не смешивались. Во всех трёх местах показывается одна подтверждённая дата. Сама форма ввода не даёт кандидату права зарегистрировать кадровое подтверждение.

POST /cases/{id}/correct-start сохраняет местное исправление, а при существующем подтверждении назначения задаёт review_required и показывает прежние кадровые сведения рядом. HR сверяет реальное назначение, при необходимости исправляет его у владельца и повторяет record-assignment с действительными данными. Новый сотрудник автоматически не создаётся. Такой ручной путь закрывает исход без брокера.

Для этапа 1 сервер предоставляет GET /cases/{id}/registration-data — только hr/admin своей организации, status=started. Ответ {case_id,case_revision,application_ref,person_ref,organization_id,department_id,position_code,starts_on,basis,transfer_mode:"manual"}. Реквизиты можно перенести вручную; это информация для кадровика, не событие RabbitMQ.

В этап 2 относятся автоматическая публикация employment.ready, приём кадровых событий, outbox/inbox, /deliveries и retry, dead-letter, broker-aware readiness, автоматическое завершение сверки и расширенная матрица распределённых сбоев.

## Проверка первого результата

| Проверка | Требуемый наблюдаемый исход |
|---|---|
| Fixture-актор или подключённая сессия | Разрешённая роль проходит, неизвестная/чужая область отклоняется |
| Requirements черновик → возврат → исправление → утверждение | Сохраняются реальные ID, источник, согласование и история |\n| Публикация новой редакции | Один current, прежняя версия остаётся доступной |
| Hiring неполный/исправленный комплект | Без обязательного принятого документа старт запрещён; новая версия не стирает оригинал |
| Чужой actor/организация | Чужие сведения и файлы недоступны |
| Повтор входного application_ref/утверждения редакции | Дубль не появляется, возвращается прежняя запись либо понятный конфликт |
| Устаревшая форма | Контролируемый конфликт без потери новой версии |
| Запуск без брокера и соседнего API | Основной HTTP-путь работоспособен |
| Рестарт | Сохранённые данные и файлы доступны |
| Ручная регистрация назначения | Hiring показывает source, автора подтверждения и фактическую дату, расхождение видно |

Расширенную инфраструктуру не нужно удалять, если она уже работает. При сдаче отметить, что реально включено. Прохождение всех автоматических event-примеров common относится к этапу 2. Сценарии fixtures/events.json и corrections.json сохраняются как его контрольные входы.
