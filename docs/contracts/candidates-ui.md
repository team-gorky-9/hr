# Candidate index and staff upload

The desktop candidate database reads `GET /api/v1/candidates`. It returns one row per application, including `response`, `manual` and external `history`, with the same assessment state as its application detail. The index contains anonymous candidate codes/headlines, channel, target, current stage and calendar days since the latest stage event. Personal contacts are read only by the existing audited application-detail route. Query parameters: `contour=training|working`, `q` (code, headline or target title, max 200), `offset` (>=0), `limit` (1..100, default 50). Response: `items`, `total`, `offset`, `limit`. Source/type filters in the current UI apply to the displayed page; the query searches the full index.

`POST /api/v1/candidates/upload?vacancy_id=<uuid>&filename=<name>&contour=training|working` accepts raw file bytes (`application/octet-stream`), not multipart. Both routes require StaffUser; working contour additionally requires the existing SearchWorkBearer credential. This does not broaden authorization. Upload requires an open, explicitly selected vacancy. TXT, DOCX and text PDF up to 10 MiB are accepted; extraction/redaction failures return 422, oversized input 413, closed vacancy or conflicting contour 409. A file is streamed with an enforced bound before extraction. No original filename is used as a filesystem path.

The adapter reuses ingest extraction, PII separation, deduplication and external-history import. It passes the selected vacancy explicitly instead of picking the newest by position/channel. A deterministic candidate code and transaction-scoped digest lock prevent repeat creation. The same file/vacancy returns 200 with `duplicate_skipped`; a new candidate/application returns 201. Successful imports identify the staff actor in the initial stage and audit event. The response is the existing ReportItem; no raw text or PII is returned. Import does not claim that model assessment has run.

Focused verification: `tests/test_candidates_http.py` passed 2 tests on a separate local PostgreSQL database with all migrations through 0014. Cases cover successful extraction/import, repeat upload, listing external history, staff-only access, contour separation, unsupported format, empty file and malformed DOCX. Public Workforce session verification returned login 201, session 200, logout 204, revoked session 401. Students and social-support currently reject Workforce tokens (401) because those backend services still only implement their explicit fixture actor contract; their UI authentication was not silently changed.
