# Первая волна · общий контракт 1.0

Для текущей сдачи Дениса (Requirements) и Ильи (Hiring) действует приоритетное [описание этапа 1](wave-1-stage-1.md). Оно сохраняет пользовательские операции и переносит брокер, outbox/inbox и расширенные распределённые проверки в этап 2. Давид продолжает Workforce по уже выданному полному контракту.

21 ноября 2026. Спецификация к реализации первой волны. Существующий API продукта продолжает действовать по своим контрактам. Новые операции, описанные здесь, ещё предстоит реализовать. Основания — принятое сервисное устройство и поручение Родиона подготовить автономные задачи.

## Изоляция поставок

| Исполнитель | Сервис / область записи | HTTP для локальной разработки | Свои миграции, тесты и compose |

| Давид | services/workforce/ | 8101 | В своей папке, собственная БД workforce |

В каждой области есть README, pyproject/lock зависимостей, запускаемый FastAPI, схема БД и миграции, тесты, compose.yml. Сервисный исходный пакет называется по области. Автор выбирает внутреннее разбиение. Стек — Python 3.13, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, PostgreSQL 17. Для первой волны RabbitMQ используется через AMQP-клиент по выбору исполнителя; задача фоновой публикации мала и не требует запуска Celery. Библиотека и версия фиксируются в сервисном lock. Общие root compose/pyproject, старые миграции и существующий API в этой волне остаются областью интегратора. Сервисы используют свои БД и учётки.

Новые сервисы не читают таблицы друг друга. Чистые валидаторы и формат требования из существующего кода можно использовать при совместимости зависимостей и автономном запуске. Удалённые ORM-модели не являются интерфейсом обмена.

## Общие HTTP-правила

Префикс каждого сервиса — /api/v1, документация OpenAPI через /openapi.json. GET /health возвращает status=ok при доступном приложении; GET /ready возвращает status=ok только при готовой БД и миграциях, иначе 503. Недоступный брокер отмечается в /ready как broker=unavailable и отдельно в доставке; сохранение предметной операции с outbox может продолжаться.

Формат JSON UTF-8, даты YYYY-MM-DD, timestamp RFC3339 с зоной. ID — UUID, если в таблице явно не указан code. Все ресурсы имеют id, revision (целое, начиная с 1), created_at, updated_at. Поля тела вне спецификации дают 422. Ошибка возвращает error с code, message, field (строка либо null), request_id (UUID либо null). Текст ошибки не включает исходные персональные документы.

Создающие/изменяющие POST и PATCH требуют Idempotency-Key UUID. Все изменения существующего ресурса также требуют expected_revision в JSON. Ключ учитывается по актору, организации, методу и пути. Повтор той же нормализованной команды возвращает исходный статус и результат с заголовком Idempotency-Replayed=true; другой запрос с тем же ключом даёт 409 IDEMPOTENCY_CONFLICT. Проверка доступа выполняется и при повторе. Сбой до commit оставляет команду повторяемой. Проверка повтора предшествует проверке старой expected_revision. Новая команда со старой ревизией даёт 409 STALE_REVISION.

Коды общего уровня — 401 AUTH_REQUIRED/INVALID_SESSION, 403 FORBIDDEN, 404 NOT_FOUND (включая скрытые чужие объекты), 409 STALE_REVISION/INVALID_STATE/IDEMPOTENCY_CONFLICT, 422 VALIDATION_ERROR, 503 DEPENDENCY_UNAVAILABLE. Пагинация GET списков — limit (по умолчанию 50, 1–100) и opaque cursor; результат items и next_cursor. По умолчанию стабильная сортировка created_at,id.

## Стендовый актор и автономный вход

Авторитетный серверный актор содержит actor_id UUID, login, organization_id UUID, grants — массив {role, scope_type, scope_id}. scope_type — organization, department или self. scope_id — UUID организации/подразделения/актора. Роли первой волны — hr, admin, department, employee, candidate. Действующее назначение может иметь несколько grants. Эти имена — учебные роли; кадровые операции ниже проверяют разрешённую организацию и предмет.

Давид реализует POST /sessions с {login,password}, ответ 201 {access_token,token_type:"bearer",expires_at,actor}; GET /session возвращает текущего актора, DELETE /session отзывает сессию (204). Пароль всех учебных пользователей — "123". Неверная пара — 401 INVALID_CREDENTIALS без различения существования логина. Сессия непрозрачная, случайная, хранится сервером, срок по умолчанию 8 часов как технический параметр стенда, настраиваемый. Роли берутся из серверных данных. Пароль и токен исключаются из логов.

У requirements/hiring AUTH_MODE=workforce означает получение актора через GET /session Workforce с тем же Bearer. При недоступном входе возвращается 503, а не новая привилегия. Для автономного старта AUTH_MODE=fixture принимает только Bearer fixture:<login> из [actors.json](../../fixtures/wave-1/actors.json), проверяет ту же область и явно пишет auth_mode=fixture в /health. Режим задаётся средой сервера, клиент его переключить не может. Локальный профиль compose запускает fixture, интеграционный — workforce. Администратор одной организации не читает другую.

Это учебная авторизация с общими паролями. На первом стенде назначения загружаются из примеров, UI администрирования и почта идут в дальнейший бэклог.

## Файлы на сервере

Этот раздел реализуют владельцы файлов **Hiring и Requirements**. Workforce в первой волне хранит ссылки document_ref и реквизиты оснований; файловые POST/GET /documents, FILE_ROOT и обработка загрузок в его поставку не входят. При необходимости проверки оригинала кадровик обращается к владельцу документа через согласованный внешний канал.

Hiring и Requirements реализуют POST /documents (multipart file и kind, возвращает 201 document), GET /documents/{id} (метаданные), GET /documents/{id}/content (поток оригинала). document содержит id, organization_id, kind, original_name, media_type, size_bytes, sha256, revision, uploaded_by. Метаданные в БД, байты в собственном FILE_ROOT. Серверный путь формируется по ID; original_name — подпись, никогда путь. MIME и размер проверяются, превышение настроенного лимита даёт 413 FILE_TOO_LARGE. FILE_MAX_BYTES задаётся средой, стартовое значение 20 MiB — стендовый параметр.

Загрузка создаёт новую неизменяемую версию-объект; исправленный документ имеет новый ID. Повтор с прежним ключом возвращает тот же объект. Файл полностью сохраняется до доступности записи; незавершённый временный файл недоступен через API. Повтор/сбой проверяются, очистка сирот не удаляет связанный документ. Скачивание проверяет право по организации и связанному делу. Точная политика конкретных документов уточнена в сервисных контрактах. Перезапуск контейнера сохраняет том.

## RabbitMQ и факт обработки

Брокер конфигурируется RABBITMQ_URL. Exchanges — w1.hiring, w1.workforce, w1.requirements, тип topic, durable. Источник пишет только свой exchange. Очередь получателя durable, имя w1.<consumer>.<event-name>; binding ключ равен event_type. Сообщения persistent, публикация с publisher confirm. Потребитель подтверждает сообщение после commit своих данных.

Envelope содержит event_id UUID, event_type, schema_version="1.0", producer, organization_id, aggregate_id, aggregate_revision integer, occurred_at timestamp, correlation_id UUID, payload. producer — имя сервиса. actor_id внутри payload для аудита не заменяет доверие к источнику. Соединения разрешены только внутренним сервисам, отдельные учётки/права exchange задаются интеграционным запуском.

В одной транзакции сохраняются предметное изменение и outbox. После подтверждения брокера outbox помечается отправленным. Получатель в одной транзакции регистрирует inbox event_id и изменение. Повтор не создаёт второй ресурс. Недоступность брокера видна через GET /deliveries?status=pending|failed|sent (hr/admin своей организации) — items {event_id,event_type,status,attempts,last_error,next_attempt_at}. Полные payload и токены не выводятся.

Transient-сбой приводит к отложенному повтору с конечным числом попыток и ручным повтором POST /deliveries/{event_id}/retry. Базовые задержки и лимит конфигурируемы; инструкции содержат фактические значения. Невалидная версия/схема отправляется в w1.<consumer>.dead с причиной. Неподходящая организация/неожиданный producer отклоняются. Запоздалая ревизия отмечается stale и не откатывает факт. Равная ревизия с другим содержимым требует сверки и не заменяет текущую запись.

## Общие сообщения

| event_type / producer | Payload | Потребитель |
|---|---|---|
| employment.ready / hiring | case_id, application_ref, person_ref, department_id, position_code, starts_on, basis {document_ref,reference,issued_on}, confirmed_by_actor_id | workforce создаёт intake, HR проверяет личность и регистрирует назначение |
| assignment.registered / workforce | intake_id, source_case_id, source_case_revision, source_event_id, employee_id, assignment_id, department_id, position_code, starts_on, revision | hiring отмечает кадровую передачу зарегистрированной |
| assignment.review-resolved / workforce | intake_id, source_case_id, source_case_revision, source_event_id, employee_id, assignment_id, department_id, position_code, starts_on, revision, resolution:"corrected"|"kept_existing", reason, reviewed_by_actor_id | hiring завершает проверку конкретного исправления и показывает фактически сохранённое назначение |
| requirements.approved / requirements | profile_id, position_code, profile_version, contour, approved_by_actor_id, approval_basis, source_document_ids | Пока демонстрационный получатель и будущий подбор. API самого сервиса даёт профиль по ID |

person_ref — {system:"legacy-hr",id:UUID,display_name:string}; он обозначает кандидатскую запись. application_ref — {system:"legacy-hr",id:UUID}. document_ref — {service:"hiring",id:UUID}; байты документа в сообщение не вкладываются. Выдача документа другому сервису требует разрешённого внутреннего чтения; в первой волне Workforce получает реквизиты основания и при необходимости запрашивает уполномоченного регистратора, а не автоматически скачивает файл чужого сервиса.

assignment.review-resolved завершает пересмотр существующего назначения. Его correlation_id повторяет correlation_id исправленного employment.ready, а source_event_id/source_case_revision указывают именно на эту принятую передачу. starts_on, department_id, position_code и revision показывают действительную кадровую запись после решения. Схема новых сообщений остаётся 1.0; тип review-resolved добавлен отдельно от прежнего assignment.registered. Hiring подписывается на оба типа. Новый пример и два альтернативных результата находятся в [corrections.json](../../fixtures/wave-1/corrections.json).

Каждый автор проверяет свои сообщения на [events.json](../../fixtures/wave-1/events.json). Это общая семантика обмена. Примеры содержат учебные ID. Локальный тестовый получатель публикует/читает эти сообщения через настоящий RabbitMQ, а не только вызывает функцию памяти.

## Подмены и начало без коллег

Автор каждого сервиса реализует в своей tests/support подмены нужных входов по настоящему контракту и этим примерам. Общие runtime-пакеты не ждём. Для hiring нужна управляемая положительная/конфликтная кадровая передача и входной пример рассмотрения. Для workforce — публикация employment.ready из fixtures. Для requirements — fixture-актор и журнал чтения события. Проверка одной и той же сериализации выполняется на producer и consumer.

После поставки интегратор включает три настоящих сервиса на одном брокере, переключает AUTH_MODE и повторяет общий путь. Локальный положительный тест с подменой помечается как автономный. Полная интеграция отмечается только после реального соединения.

## Совместимость и управление изменениями

Документы wave-1 и fixtures/wave-1 поставляются вместе отдельной базой. Исполнители создают ветки от указанного в карточке доступного SHA. Менять общий формат в своей реализации молча нельзя — вопрос с примером передаётся Родиону/архитектору. Добавляемые поля требуют проверки потребителя. Внутренние имена таблиц и порядок слоёв выбирает исполнитель.

Существующие контракты requirements/import/api остаются доступными существующим callers. Новые сервисы первой волны не переписывают старую БД и не переключают старое API автоматически. Единственного владельца записи и перенос данных определяет отдельная интеграционная поставка.
