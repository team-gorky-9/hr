# Применимость отклика к профилю · v1.0

Реализовано в `feature/profile-assessment-integration` по разрешению Давида. Исходное обсуждение сохранено в [предложении](profile-applicability-proposal.md). Это правило маршрутизации оценки, не оценка качества кандидата и не утверждение профилей работодателем.

## Вход и решение

Общий `app.assessment.applicability.resolve_applicability` получает код целевой должности и `applications.posting_title`. Версионируемая политика — `app/assessment/policies/hr-consultant.json`. Она охватывает только hr-consultant; для других должностей возвращается `None` (политика не задана).

Сравнение точное после NFC, casefold и схлопывания пробелов. Подстроки, сходство названий и папка импорта не подтверждают соответствие. Две явные другие должности — «Сметчик» и «Начальник отдела внутреннего финансового контроля, аудита и закупок» — дают mismatch. Пустое название даёт unresolved/missing_posting, остальные названия — unresolved/unreviewed_mapping. Положительных соответствий в начальной политике нет.

Чтобы добавить confirmed, нужна явная строка с posting_title, status, reason, source и responsible; версия политики повышается. source/responsible фиксируют основание решения, а не генерируются моделью. Повтор названия после нормализации и неизвестное поле — ошибка конфигурации. Результат содержит status, reason, policy_version, SHA-256 политики, входной snapshot и SHA-256 snapshot.

## Где применяется

`assess_in_context` проверяет владельца отклика, целевую должность, контур кандидата/профиля и все params до модели. primary допускает прямой отклик на целевую должность; history не становится основным откликом. Для покрываемой политикой должности только confirmed проходит к оценке. mismatch и unresolved дают skipped, не создают assessment, не меняют этап и не превращаются в not_met.

comparison задаётся явно и может оценить ту же пару кандидат/профиль независимо от названия исходной публикации, если контур и статус профиля допустимы. Нового отклика нет. Результат пары может повторно использоваться при совпадении текста, профиля, алгоритма, промпта и as_of. Каждый запуск сохраняет отдельный manifest в audit_log с action=other, entity_type=assessment_run. Успешный manifest содержит ID/версии текста, карточки, профиля, оценки, purpose, mode, as_of и решение политики; skipped содержит причину и assessment_id=null.

В списке и карточке API используется тот же resolver, в том числе для уже сохранённых оценок. mismatch → assessment_status=not_applicable; unresolved → mapping_required. В обоих случаях основной assessment/formal_result/overall_score не показывается. Список по умолчанию сохраняет все импортированные отклики; фильтр applicability задаётся явно. Отдельный GET comparison возвращает оценку с целевой должностью и происхождением.

## Полный пример

Импорт создал отклик с posting_title=«Сметчик» в папке консультанта. CLI primary передаёт ID отклика и профиль hr-consultant. Resolver возвращает mismatch/different_role. Оркестратор записывает skipped и не вызывает модель. API показывает исходную публикацию и not_applicable; кандидат остаётся на своём этапе. Если пользователь явно запускает comparison, допустимый оценщик создаёт оценку пары. Она доступна по comparison, но обычная карточка отклика по-прежнему не представляет её результатом основного отбора.

## Область замера

В реальном архиве с SHA-256 `14a9a8432396a32abba0221c76410d3482bac288a18325d3fcbd7c138e5e7fd2`: 287 записей, 21 mismatch, 266 unresolved (45 без подвала, 221 без подтверждённого сопоставления), 0 confirmed. Это записи откликов, не уникальные люди. T-13 нельзя считать на 21 записи как на «слабых консультантах»; основная выборка до подтверждения сопоставлений пуста. Сравнительный прогон маркируется отдельно.
