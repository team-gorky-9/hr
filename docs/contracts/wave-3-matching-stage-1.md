# Волна 3 · двунаправленный подбор · этап 1

Три небольших задачи Ильи поверх существующих поиска и кросс-оценки. Сохраняются их схемы и семантика. Новая модель, новый брокер и отдельный вычислительный сервис для этой поставки не требуются. [Поиск](search.md) · [API кросс-оценок](api.md)

Новые операции находятся в legacy API /api/v1/matching, только для текущих HR/admin. Для working применяется действующая политика доступа к рабочему поиску и источникам; секрет поискового прокси хранится сервером. Training остаётся явно помеченным. Сохранённая подборка не даёт права на контакт или кадровое решение.

## Вход без ожидания соседей

VacancySnapshot = {ref:{system,id},revision,title,description,position_code,status:published|closed,contour:training|working,observed_at,profile_ref:null|{system,id,version},search_query}. system — catalog либо legacy-hr. UUID в ref обозначает источник; одинаковые названия не склеиваются. search_query — выбранное HR описание нужной работы, до 512 символов по правилам текущего поиска. Текст объявления не обрезается автоматически ради вместимости query.

Вход может быть явно предоставленным HR снимком или snapshot из доступного API каталога. Ответ указывает source_mode=provided|catalog_api и observed_at. Если подключение каталога недоступно, операция с предоставленным учебным snapshot работает самостоятельно. Разница контуров или закрытая публикация отклоняются, состояние запроса не изображается свежей проверкой внешней площадки.

## 3A · найти людей под вакансию

POST /matching/candidates принимает {vacancy:VacancySnapshot,filters,limit}. filters и limit идентичны действующему SearchRequest. Передать search_query в существующий механизм поиска по профессиональному тексту. Непустые фильтры и права применяются до выдачи.

Ответ {vacancy_ref,vacancy_revision,observed_at,source_mode,contour,unit:"candidate_record",items,matching_status:"completed"} сохраняет items действующего search-контракта. Для каждого результата добавляется qualification_status=not_evaluated либо результат **действительно найденной актуальной оценки** по точному profile_ref. Если сопоставления профиля нет, это явно not_evaluated, поиск не выдаёт формальный допуск. Цитата и источник у результата остаются проверяемыми.

При нуле совпадений — 200 с пустым items. При недоступном поиске — 503 SEARCH_UNAVAILABLE, без выдуманного пустого успешного результата. Профессиональное совпадение, право контакта и наличие прежнего отклика показываются отдельно в своих доступных полях.

Демонстрация — открытая учебная вакансия с запросом про требования к ИС на существующем учебном корпусе, подходящий фрагмент; второй запрос с отсутствующим обязательным термином даёт пустой результат. Подключение нового сервиса вакансий не требуется.

## 3B · найти вакансии по присланному резюме

POST /matching/vacancies принимает {candidate_id,contour,vacancies:[VacancySnapshot],limit}. candidate_id — текущая запись резюме legacy, до 50 предоставленных вакансий на запрос, limit 1..50. Сервер проверяет доступ к кандидатской записи и контур. Источник списка явно provided либо при настроенном адаптере catalog_api.

Использовать существующее чтение cross-assessments и связывать только точный профиль/версию и должность с опубликованной вакансией. Нельзя сопоставлять профиль по похожему названию. В первой самостоятельной поставке учебные вакансии ссылаются на реально сохранённые legacy-профили из своих фикстур. Ссылки на новый Requirements без подтверждённого отображения считаются unmapped_profile.

Ответ {candidate_id,current_text_id,contour,source_mode,items:[{vacancy_ref,vacancy_revision,title,profile_ref,assessment_status,formal_result:null|string,assessment_id:null|UUID,reason}],needs_evaluation:[{vacancy_ref,title,reason}],excluded:[{vacancy_ref,reason}]}.

items содержат опубликованные вакансии с доступной текущей оценкой по точному профилю, включая met, unknown и not_met с понятным основанием. Порядок — met, unknown, not_met, внутри равенства по стабильному ID публикации. Этот простой порядок первой версии выводится из действующих формальных результатов, без нового суммарного процента.

needs_evaluation содержит открытые вакансии без оценки, с устаревшей оценкой или несопоставленным профилем с разными reason. Закрытые и вакансии другого контура — excluded без чужих подробностей. Если отсутствуют готовые оценки, HR видит список требующих проверки и причину, а не утверждение «подходящей работы нет».

Сохранённый результат не гарантирует пригодность или приглашение. Новый отклик создаётся отдельной операцией подбора. Новая модель для этого запроса не вызывается.

Демонстрация — одна кандидатская запись, две опубликованные вакансии с сохранёнными учебными результатами и одна без оценки. Показать основания, needs_evaluation и исключение закрытой вакансии. Пользовательские данные и живой LLM не нужны; использовать контролируемые существующие фикстуры.

## 3C · подборка HR по новой публикации

POST /matching/suggestions принимает тот же вход, что matching/candidates, выполняет тот же поиск и сохраняет снимок результата. Ответ 201 {id,vacancy_ref,vacancy_revision,created_at,created_by,contour,source_mode,items,qualification_note}. GET /matching/suggestions/{id} перечитывает снимок по праву текущего кадрового актора/контура.

Это доступное действие для экрана после публикации вакансии: фронтенд вызывает его и показывает найденные записи. Сохранённый снимок помечен своей датой и редакцией вакансии. Нужен новый результат — новый вызов, старый сохраняется для объяснения. При повторном создании могут появиться две версии расчёта, но кадровых записей, приглашений и откликов эта операция не создаёт.

Хранить только разрешённую выдачу и версии источников. При чтении проверять доступность исходного источника; отозванный/недоступный текст не раскрывать из сохранённой копии. Снимок сохраняет факт расчёта, состояние «источник недоступен» и идентификаторы в разрешённой области. Сроки хранения и полный отзыв производных данных уточняются при проектировании общего механизма; обход текущего доступа недопустим.

В текущем этапе вызов после публикации является явной частью API-пути, а не обещанием фоновой доставки события. До подключения каталога тот же путь проходит с учебным snapshot. Автоматический триггер RabbitMQ и фоновая очередь — этап 2.

Демонстрация — предоставить опубликованную вакансию → получить подборку → перечитать её по ID → повторить с новой редакцией и увидеть два датированных результата. Ни один из них не создаёт отклик и не включает человека в официальный резерв.
