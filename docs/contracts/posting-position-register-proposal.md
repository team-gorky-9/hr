# Предложение формата реестра публикаций · 0.1

**Статус:** предложение Давида к согласованию Родионом с Денисом и Ильёй, не действующий контракт приложения. **Дата:** 2026-11-20. [Пакет и вопросы HR](../../fixtures/posting_positions/README.md). Действующая [политика применимости](profile-applicability.md) 1.0 сохраняется.

## Граница

Реестр описывает решение о связи публикации с должностью. Он не оценивает кандидата, не создаёт отклик и не меняет архивные поля. Для текущей поставки это JSON с полными строками; подключение к приложению требует согласования общего стыка. Существующая модель `Policy` принимает только `confirmed/mismatch` и не поддерживает этот формат напрямую.

## Поля строки

| Поле | Смысл |
|---|---|
| `id`, `register_version` | Стабильный ID строки и версия неизменяемого набора решений. Версия схемы отдельно в `format_version`. |
| `context` | Канал, идентификатор и SHA-256 набора, исходная папка, опциональный подтверждённый employer_id. Папка сохраняет происхождение, но не даёт подтверждения. |
| `posting_title`, `source` | Буквальное название из подвала основного отклика и происхождение. История внешних откликов не является заменой. |
| `decision_state` | `confirmed`, `needs_review`, `no_matching_position`. Последнее требует явного решения владельца об отсутствии подходящей должности в каталоге. |
| `position_code` | Один код только при `confirmed`; иначе null. Несколько возможных кодов — причина сверки, не массив подтверждений. |
| `decision_author`, `decision_date`, `decision_basis` | Уполномоченный решающий, дата `YYYY-MM-DD`, ссылка на основание. Для отсутствующего решения null. Назначенный исполнитель не является автором кадрового решения. |
| `evidence_refs`, `observation` | Проверяемые материалы и предметное наблюдение, не утверждение. |
| `open_question`, `follow_up_owner`, `decision_owner_role` | Что выяснить, кто получает ответ и чья компетенция нужна. |
| `document_count` | Частота в закреплённом архивном срезе, не число уникальных кандидатов и не текущий счётчик БД. |
| `current_policy` | Отдельное свидетельство существующего поведения относительно hr-consultant: статус, версия и хэш политики. Не превращается в decision_state. |

Ключ чтения должен включать контекст и название, а не одно глобальное название. Алгоритм нормализации и доступность dataset/employer-контекста в отклике требуется согласовать с Денисом: текущий resolver получает только position_code и posting_title. Недостающий контекст, несколько совпадений, новая публикация и противоречивые основания оставляют связь неразрешённой. Нельзя автоматически экспортировать положительные записи этого пакета в старую политику без сохранения контекста.

`missing_publication` — отдельный результат с причиной `missing_posting`, отображением «Исходная публикация неизвестна» и частотой. Пустое название не становится строкой «не существует подходящей должности».

## Предлагаемая цепочка потребителя

1. Взять `application(source=response)`, буквальный `posting_title` и подтверждённый контекст импорта.
2. Выбрать конкретную версию реестра. Найти однозначное решение в том же контексте. При отсутствии названия вернуть missing_posting; при новом названии или недостающем контексте — причину сверки.
3. Только для confirmed разрешить код в существующий position_id, затем найти действующий approved-профиль своего контура. Если его нет, показать отдельно «нет действующего утверждённого профиля». Не создавать должность и не использовать draft.
4. Сохранить версию/хэш реестра, ID решения, версию/UUID профиля, purpose и состав выборки в манифесте запуска. T-13 читает закреплённые версии, новая редакция не меняет опубликованный срез. Механизм хранения и воспроизведения остаётся на согласовании.
5. Исходные vacancy_id, posting_title, история и этап не меняются. Явное comparison показывает собственное назначение «повторное рассмотрение» и целевой профиль. В рабочую воронку идут source=response.

## Полный пример

Импорт сохранил отклик «Сметчик» с vacancy_id из папки консультанта. Давид добавляет исходное название, частоту 1, контекст архива, ДИ и вопрос HR. Решения владельца ещё нет: needs_review, position_code=null. Уже действующая политика hr-consultant даёт mismatch и блокирует primary. Кадровик должен видеть название и причину отсутствия исходной оценки. Если HR позже подтвердит отсутствие подходящей должности, новая версия получает no_matching_position с автором, датой и документом; это не отказ кандидату. Явное comparison по допустимому профилю остаётся отдельной операцией и не создаёт отклик.
