## 1. Назначение и границы

Профиль одной должности состоит из условий допуска (`formal_requirements`) и компетенций (`competencies`) с индикаторами (`indicators`). Формат одинаков для консультанта и Python-разработчика. Автор сохраняет происхождение каждой строки, обязательность, способ проверки и критерии исходов; оценщик сопоставляет их с фактами кандидата.

Файловый пакет и вход БД — разные представления. Публичное преобразование выполняет [app/requirements/package.py](../../app/requirements/package.py), запись — [app/db/repository.py](../../app/db/repository.py), схемы строк — [app/schemas/requirements.py](../../app/schemas/requirements.py). Прежний `scripts.load_requirement_profiles` сохранён для существующих клиентов. `python -m app.requirements load-package` принимает пакет 0.2, а `load` — нормализованный одиночный черновик; старые примеры сигнатур v0.1 не являются действующим API.

Основания: Денис согласовал единый формат; Илья принял `params`, альтернативы и этапы, уточнил стаж, `same_as` и `basis` 20.11.2026. ### 3.1. Образование и альтернативы

У каждой альтернативы свой стабильный ключ, результат и цитаты. Внутри альтернативы все условия обязательны; между альтернативами — «или»: хотя бы одна подтверждена → `met`; все опровергнуты → `not_met`; иначе `unknown`. Ключи альтернатив различаются внутри условия.

`requires_requirement` связывает проверку направления с уровнем соответствующей записи образования. Неизвестный уровень даёт `unknown` по направлению. `not_met` по уровню не переносится автоматически. Вариант с `retraining_fields` требует подходящей профессиональной переподготовки вместе с высшим образованием; отсутствие упоминания курсов не доказывает отсутствие переподготовки.

В данных используются `level="высшее"`, `field_group="technical"`, `enrollment_status="senior_student"`. `field_examples` и `field_exclusions` задают явные включения/исключения; пустые списки не означают «любая специальность подходит». Пограничное направление → `unknown` и вопрос. Коды ОКСО по памяти в контракт не включены; команда приняла пять положительных примеров technical, без исчерпывающего списка и без диапазона кодов. Senior_student подтверждается явным заявлением; один номер курса при неопределённом пороге даёт unknown с объяснением ограничения правила. Точные критерии — в [content-decisions.md](../../fixtures/requirement_profiles/content-decisions.md).

В карточке v1.4 (PR #8, включён в снимок #10) реализованы уровни `высшее`, `неоконченное высшее`, `среднее профессиональное`, `среднее общее` и `level_raw`. Старые свободные значения нормализуются при чтении; нераспознанное → level=null, исходный текст — level_raw. Неизвестное значение кандидата означает `unknown`, а не `rule_unsupported`.

Новые необязательные поля: Education.status (`completed`, `in_progress`, `incomplete`), course 1–6, field_code; Course.kind (`retraining`, `qualification_upgrade`, `other`), completed, field, hours; Experience.kind (`work`, `internship`, `contract`, `project`). Даты опыта допускают YYYY / YYYY-MM / YYYY-MM-DD без выдумывания недостающей точности. Они приняты Денисом и реализованы в PR; после интеграции можно перенести подтверждённые факты из card_limitations в карточки. Текущие 41 карточка уже принимаются новой схемой без изменения файлов.

### 3.2. Опыт

Месяцы включительные, пересечения объединяются. Текущее место считается до фиксируемого `as_of` формата `2026-11`. Для неполных дат гарантированные интервалы объединяются отдельно от возможных: L — от самого позднего начала до самого раннего конца, U — от самого раннего начала до самого позднего конца. Пустой гарантированный интервал даёт 0. Без дат — `[0, ∞]` до учёта вида записи.

Для коммерческого опыта оплачиваемая работа на работодателя (`work`, `contract`) входит в L и U; `internship` и неизвестный вид — только в U; учебный/личный `project` не входит ни в одну. Стажировка с явным трудовым договором классифицируется как `work`. Вид нельзя угадывать по типу организации.

При пороге T: `L ≥ T` → `met`, конечная `U < T` → `not_met`, иначе `unknown`. Пустой раздел или «Не указано» всегда `unknown`. Заявление о коммерческом стаже сопоставляется с периодами: одинаковый исход сохраняется, расхождение чисел отмечается; разные исходы → `unknown` и ручная сверка. При неизвестном исходе периодов заявление внутри `[L,U]` может дать результат. Общий стаж без уточнения коммерческого — только верхняя граница: при T=24 «1 год» даёт `not_met`, «3 года» — `unknown`. Подробности и границы покрытых сочетаний — в [правилах ожиданий](../../fixtures/requirement_profiles/evaluation-rules.md).

Контрольные значения: перекрывающиеся 2021-01–2023-01 и 2022-01–2024-01 дают 37 месяцев; 2022–2022 → `[0,12]`; 2019–2023 → `[38,60]`; 2021–2023-06 → `[19,30]`.

Для реального `relevant_role` без минимума месяцы не считаются: рабочий контекст с релевантными обязанностями и цитатой → `met`; явное отсутствие соответствующего опыта → `not_met`; учебный/личный проект, неясный контекст или отсутствие сведений → `unknown`. Давид принял применимость работы, стажировки и договора к этой ДИ: собственные технические обязанности Python либо SQL/ETL/BI. Работа с данными без Python допустима для этого условия; Python проверяется отдельными индикаторами. Общего упоминания отчётов недостаточно. Отсутствие минимума не означает автоматический `met`.

## 4. Этап и основание результата

Формальный итог относится только к обязательным условиям с `check_stage=screening`: приоритет `not_met` > `unknown` > `met`. Компетенции и желательные строки его не меняют. Требования интервью входят в общее ядро вопросов по должности; отсутствие интервью не ухудшает допуск по резюме.

`verification` — свойство требования, `basis` — фактическое основание результата. Оба используют `resume | documents | interview | test`; отдельного `document` нет. В v1.5 предварительность задаётся точным правилом: `result != unknown` и `basis != verification`. Это сравнение способов, а не иерархия их «силы». Предварительным может быть как met, так и not_met; unknown предварительным не помечается.

**Принятое решение:** подтверждённое по резюме образование сохраняет `met`, `basis=resume`, `is_preliminary=true` при verification=documents. Оно участвует в формальном итоге как met. `assessments.formal_preliminary=true` только когда итог met и хотя бы одно обязательное screening-условие предварительно. Пользователь видит «по резюме, нужен документ». Пять положительных образовательных ожиданий пакета остаются прежними; повторное согласование выбора статуса не требуется.

В v1.5 `formal_checks` хранит `basis`, `is_preliminary`, `alternatives`, `confirmed_by_user_id`; временное размещение основания и альтернатив только в explanation больше не является целевым форматом. `FormalCheckIn` принимает `alternatives: [{key, result, evidence}]`, но не basis/is_preliminary: `save_assessment` сам устанавливает basis=resume и вычисляет предварительность. Цитаты каждой альтернативы проверяются по тексту карточки.

Вход alternatives для совместимости допускает пустой список; непустой должен содержать все ключи условия ровно по одному. Для met требуется подтверждённая альтернатива, для not_met — опровержение всех. Итог unknown БД принимает всегда, в том числе при подтверждённой альтернативе: зависимость requires_requirement обрабатывает оценщик. Пустой список, хотя принимается БД, не доказывает исполнение требования «результат и цитаты по каждой альтернативе».

Подтверждение человеком через `confirm_formal_check` создаёт новую версию оценки с basis=documents/interview/test; нужны активный hr/admin, текущая оценка и непустой comment. Заменяемая строка получает пустые evidence/alternatives: основание описывает comment, старые цитаты остаются в истории. Остальные результаты копируются, предварительность и итог пересчитываются. Формат человеческого подтверждения не требует выдумывать цитату из резюме для диплома.

**Оставшаяся адаптация:** `_apply_basis` ветки Ильи `c94285e` ещё понижает met до unknown; оценщику нужно перейти на поля v1.5 и сохранить исходный met. Старый [assessment.md](assessment.md) в рабочем checkout и его временный explanation должны быть синхронизированы владельцем при интеграции. Проверка схем и функции предварительности не является прогоном оценщика.

## 5. Счётчики компетенций и повторы

До утверждения шкалы `competency_scores.level=null`. Вместо процентов — «подтверждено X из Y» отдельно для обязательных и желательных, по компетенции и профилю. Подтверждение/опровержение требует содержательно подходящей цитаты; отсутствие сведений не равно противоречию.

В знаменатель screening входят только индикаторы этого этапа, не исключённые из оценки. Интервью и `excluded_from_scoring=true` показываются отдельно. Итог профиля — сумма единиц по компетенциям. Результаты и временное хранение счётчиков в `competency_scores.explanation` определяет [assessment.md](assessment.md) §4.5.

`same_as` — общий непустой ключ на строках группы, а не цепочка ссылок. Все участники находятся в одной компетенции, на одном `check_stage`, без исключённых индикаторов. Нарушение — ошибка проверки пакета. Группа даёт одну единицу; она обязательна, если обязателен хотя бы один участник.

| Статусы участников | Статус группы |
|---|---|
| Есть подтверждение, остальные без сведений | подтверждено |
| Есть противоречие, подтверждений нет | противоречит |
| Есть подтверждение и противоречие | противоречит + ручная сверка |
| Все без сведений | нет сведений |

В Python v5 связаны `py.di.P112` и `py.di.P209` общим `py.same-as.personal-data-law`: обе строки SECURITY, обе на интервью. В знаменатель резюме группа не входит. Строка применения ПДн `py.di.P134` самостоятельна. Одна цитата может доказывать разные навыки; совпадение цитат не создаёт `same_as` автоматически.

### 6.2. Жизненный цикл и синтетика

В v1.5 не более одного approved на должность **в каждом контуре**. Утверждение требует человеческого основания; корректный JSON и успешная загрузка не утверждают содержание. У кандидата и профиля is_synthetic задаётся при создании и защищён от изменения триггером. Импорт py-9001 должен создавать учебного кандидата; старую реальную запись нельзя просто переключить флагом.

Правила допуска через repository.save_assessment v1.5:

| Кандидат | Профиль | Сохранение оценки |
|---|---|---|
| Реальный | Реальный approved | Рабочая оценка |
| Реальный | Реальный draft либо любой учебный | Отклоняется |
| Учебный | Реальный или учебный, draft/approved | Учебная оценка |
| Любой | Archived | Отклоняется |

Оценка учебная, если учебный кандидат **или** профиль: функция is_training_assessment. В API предусмотрено is_training и пометка «Учебный пример — не рабочая рекомендация»; рабочие списки должны исключать учебные данные. Это контракт API, не подтверждение готовности маршрутов/интерфейса.

Решение Родиона снять запрет реализовано Денисом через разделение контуров, без вытеснения реального approved. В окончательном ответе Илья подтвердил следующий контракт сервиса после интеграции #10:

| Режим оценщика | Кандидат | Выбор профиля |
|---|---|---|
| `operational` | Только реальный | `get_approved_profile(session, position_id)` — рабочий approved |
| `technical` | Только учебный | По умолчанию `get_approved_profile(..., synthetic=True)`; явный `--profile-id` допускает реальный или учебный draft/approved |

Archived запрещён в обоих режимах. Несовместимый кандидат/профиль отклоняется сервисом до вызова модели. Эти проверки режима строже таблицы repository: БД проверяет совместимость кандидата и профиля, но не получает имя CLI-режима. В частности, допустимость сохранения реального кандидата с рабочим approved не разрешает запускать его в technical.

Устаревшая таблица technical в assessment.md должна быть заменена владельцем при адаптации. Решение согласовано; реализация в ветке Ильи `c94285e` ещё прежняя. Миграция и транзакционные сценарии в этом шаге локально не запускались.

### 7.1. Согласованный протокол проверки 41 случая

По двум окончательным ответам Ильи, переданным участником, существующие ожидания остаются независимым эталоном. Дополнять все случаи полной разметкой оценки не требуется. У каждого случая есть текст, карточка, доказательства и целевой `rule_key`; это адресная проверка, а не эталон всех строк профиля.

1. Сравнивается `expected.result` только по `rule_key`. Итог профиля и остальные ключи не сравниваются. Отсутствующее ожидание не означает ожидаемый `unknown`.
2. Для прогона с подставленными ответами модели Илья собирает вход из фактов карточки, цитат и результатов альтернатив случая. По остальным ключам `no_info` — только заглушка окружения теста. Нельзя подставить готовый итог вместо исполнения проверяемого правила и назвать это проверкой алгоритма.
3. Исключение — `requires_requirement`: зависимый уровень берётся из фактов случая. В четырёх `education_field`-случаях сведения об уровне и альтернативы заданы; если адаптеру не хватает конкретного факта, Илья передаёт список ID для точечного дополнения. Полная разметка всех ключей заранее не нужна.
4. Код сам ищет цитаты; найденные позиции сравниваются с размеченными. Живой YandexGPT сверяется с тем же эталоном; ошибки извлечения и исполнения правил отмечаются раздельно.
5. Два случая `rule-unknown-key` и `rule-unknown-version` проверяют отказ всей оценки: `RuleUnsupportedError` до первого вызова модели, без сохранения оценки и без записей вызовов модели. Это не `unknown` кандидата. Отдельный отказ загрузчика проверяется на стороне Дениса.
6. `same_as` проверяется после появления хранения отдельным синтетическим примером screening-группы: смешанная обязательность, подтверждение и противоречие, ручная сверка. Ожидания уже описаны в [evaluation-rules.md](../../fixtures/requirement_profiles/evaluation-rules.md). Реальные P112/P209 относятся к interview и не входят в Y разбора резюме.

Последовательность Ильи: ai-01 отдельно → интеграция #10 и адаптация предварительности, этапов/альтернатив и режимов → 41 адресная проверка с подставленными ответами и на живой модели. После следующего изменения хранения Денисом — проверка same_as. Прогон 41 случая не ждёт хранения дублей. Ни один из этих будущих прогонов здесь не заявлен выполненным.
