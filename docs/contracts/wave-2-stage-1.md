# Вторая волна · первые функциональные задачи

Спецификация к реализации по утверждённому порядку 21 ноября 2026. База — hr/main 376b9b4 с Workforce и Hiring этапа 1. Здесь описаны три небольших следующих результата. Остальные функции второй волны выдаются отдельными задачами после них. Брокерная доставка и выделение новых сервисов не являются условиями этой сдачи.

## Общие условия

Сохраняются форматы ID/дат, область организации, JSON-ошибки, права и поведение уже работающего владельца. Новые ресурсы получают revision с 1. Изменение существующего ресурса принимает expected_revision, конфликт — 409 STALE_REVISION. Ошибки состояния — 409 INVALID_STATE, неверный вход — 422, чужой объект — 404. Идемпотентный общий движок, очередь и тяжёлые испытания не добавляются.

Одного короткого успешного HTTP-пути, перечитывания результата и критичной отрицательной ситуации достаточно для демонстрационной проверки. Новая модель и расход токенов внешнего LLM для этих задач не нужны.

## Давид · назначить вводную программу сотруднику

Реализовать самостоятельный модуль внутри существующего services/workforce. Он использует готовые сессии, кадровые данные и БД владельца. Публичный префикс /api/v1/onboarding. Его дальнейшее выделение в карьерный сервис — этап 2.

Первый результат — HR назначает вводную программу по существующему кадровому назначению, сотрудник видит шаги, отмечает ознакомление, HR видит прогресс. Эта задача охватывает организационное ознакомление. Экспертная проверка рабочих заданий и полноценное закрытие адаптации будут следующей отдельной функциональной задачей.

В repeatable seed добавить шаблон intro-v1 с тремя информационными шагами: прочитать вводный материал, ознакомиться с контактами/порядком работы, ознакомиться с планом первого дня. Материалы — явно учебные. Template содержит code,version,title,steps [{key,title,description,material_url:null|string,kind:"acknowledgement"}]. В первой поставке шаблон фиксирован, редактор программ не требуется.

Program содержит id,organization_id,employee_id,workforce_assignment_id,template_code,template_version,assigned_by_actor_id,assigned_at,revision,status active/intro_completed/cancelled, steps [{key,title,description,material_url,acknowledged_at:null|timestamp,acknowledged_by:null|UUID}], completed_count,total_count,cancel_reason:null|string. Состав шаблона копируется в назначенную программу, текущие кадровые данные читаются по ссылке.

| Операция | Вход и результат | Правило |
|---|---|---|
| GET /onboarding/templates | → items учебных Templates | HR/admin и employee своего контура |
| POST /onboarding/programs | {workforce_assignment_id,template_code,template_version} → 201 Program | HR/admin своей организации; существующее действующее назначение на дату запроса. Нет допустимого основания — 409 ASSIGNMENT_NOT_ACTIVE. Повтор той же пары назначение+версия шаблона возвращает существующую программу с 200 |
| GET /onboarding/programs | → items | HR/admin своей организации, employee — только связанный Employee.account_actor_id |
| GET /onboarding/programs/{id} | → Program | Те же права по объекту |
| POST /onboarding/programs/{id}/steps/{key}/acknowledge | {expected_revision} → Program | Только собственный employee. Повтор уже отмеченного шага возвращает прежнюю отметку; HR не отмечает ознакомление от имени человека |
| POST /onboarding/programs/{id}/cancel | {expected_revision,reason} → Program | HR/admin, причина обязательна, подтверждения и история сохраняются |

Последний шаг переводит active в intro_completed. Это итог вводной программы, не решение об испытании/кадровой пригодности. После окончания кадрового назначения новые отметки запрещены, GET показывает assignment_state=inactive и прошлый прогресс; HR может завершить организационное состояние через cancel. При переводе появляется новое основание для отдельной программы. Без связи Employee с actor HR видит account_link_required, чужая учётка не получает программу.

Короткий пример — назначить intro-v1 сотруднику, войти связанным employee, отметить три шага, перечитать 3/3 и intro_completed. Другая employee-учётка не видит программу. Повтор отметки не увеличивает счётчик.

## Илья · зафиксировать результат телефонной встречи

Расширить существующий legacy API app/api/interview и модель Interview. Использовать существующий StaffUser и заголовок X-User-Login этого API; серверные session-токены Workforce не объявлять автоматически совместимыми. Область задачи — окончание одной телефонной встречи и чтение её результата. Повторное рассмотрение, ручная правка резюме и отдельный сервис интервью относятся к следующим карточкам.

Существующий InterviewResult уже содержит pending, continue, stop, no_answer. Сохранять эти значения. Добавить revision с 1 для существующих строк и outcome_recorded_at:null|timestamp, attempt_at:null|timestamp. Точный способ истории выбрать внутри текущего продукта без изменения чужих миграций.

| Операция | Вход и результат | Правило |
|---|---|---|
| GET /applications/{id}/interviews | → items {id,kind,scheduled_at,held_at,attempt_at,result,summary,interviewer_user_id,outcome_recorded_at,revision} | HR/admin по правилам существующего API, только доступный отклик |
| POST /interviews/{id}/outcome | {expected_revision,result:"continue"|"stop"|"no_answer",occurred_at,summary} → та же форма Interview | HR/admin, kind=phone, pending. Проводивший — текущий подтверждённый актор. Department-встреча возвращает 409 UNSUPPORTED_INTERVIEW_KIND |

Для continue/stop occurred_at записывается в held_at и attempt_at, интервьюер берётся из актора, summary обязателен и содержателен. Для no_answer attempt_at заполнен, held_at=null, пользователь видит несостоявшуюся попытку. outcome_recorded_at — время записи сервером. Ошибочное время/пустое пояснение → 422. Итог встречи сам не меняет этап отклика, не оформляет отказ и не создаёт резерв.

Повтор в точности той же команды того же актора возвращает прежний результат без нового факта. Иной итог завершённой встречи даёт 409 INTERVIEW_ALREADY_COMPLETED; исправление итога отдельной командой — следующая функциональная задача. Право проверяется до возврата результата. Параллельные команды не перезаписывают один завершённый итог.

Существующая генерация гайда после завершённой встречи может создать следующую pending по своей логике; сохранённый гайд и ответы старой встречи остаются доступны. Проверь этот участок адресно. Для демонстрации создать учебную pending существующим fixture/helper без живого LLM, завершить continue, прочитать дату/интервьюера/итог. Отдельный no_answer остаётся без held_at. В отчёте указать, какой endpoint фронтенд использует для чтения факта.

## Денис · создать, опубликовать и закрыть вакансию

Следующая задача после его текущего этапа 1 требований. Реализация внутри services/requirements, отдельный каталог /api/v1/catalog/vacancies. Область первого результата — одна внутренняя публикация на портале по действующему профилю. Заявка подразделения с количеством, несколько внешних каналов и автоматический подбор архивных кандидатов — следующие функциональные карточки.

Vacancy содержит id,organization_id,department_id UUID,position_code,title,description,profile_id UUID,profile_version integer,revision,status draft/published/closed,created_at,updated_at,published_at:null|timestamp,closed_at:null|timestamp,close_reason:null|string. department_id берётся из проверенного учебного справочника/переданной разрешённой области. Для разработки не нужен вызов живого Workforce. profile_id должен обозначать утверждённый профиль собственной организации/позиции.

| Операция | Вход и результат | Правило |
|---|---|---|
| POST /catalog/vacancies | {department_id,position_code,title,description,profile_id} → 201 Vacancy | HR/admin своей организации, заголовок и описание непустые |
| GET /catalog/vacancies | ?status=… → items | HR/admin своей организации |
| GET /catalog/vacancies/{id} | → Vacancy | Те же права |
| PATCH /catalog/vacancies/{id} | {expected_revision,title?,description?,profile_id?} → Vacancy | Только draft, неизменяемая история прежней редакции сохраняется |
| POST /catalog/vacancies/{id}/publish | {expected_revision} → Vacancy | draft → published, проверить текущую применимость утверждённого профиля. Нет подходящего — 409 PROFILE_NOT_READY |
| POST /catalog/vacancies/{id}/close | {expected_revision,reason} → Vacancy | draft/published → closed. Причина обязательна, существующие отклики от этого автоматически не меняются |
| GET /public/vacancies | → items {id,title,description,position_code,published_at} | Только published; публичная проекция без внутренних источников, акторов и комментариев |

Публикация даёт открытый API каталога портала. Размещение на HH/Работе России здесь не заявляется. После закрытия запись исчезает из публичного списка, HR видит историю. Опубликованные условия в этой задаче неизменяемы; для существенного изменения закрыть и создать новое объявление со своими данными. Поддержка версий открытого объявления — последующая задача.

Короткий пример — собственный approved профиль → draft → исправление → publish → запись в публичном списке → close → исчезновение из публичного списка. Чужой профиль и черновой профиль не дают публикации. Источник требований используется без вызова модели.

## Условия независимой работы

Давид использует свой готовый Workforce, Илья — существующий подбор, Денис — результат собственной текущей задачи. Никто не ждёт незавершённый сервис другого участника. На уровне конкретного HTTP-пути нужны только реально используемые входы. Все новые операции документируются и проверяются коротко; отдельные сценарии и границы этапа 2 фиксируются в парных карточках.
