# Волна 4 · кадровая картина · этап 1

Три небольших задачи Ильи на основе уже реализованной отчётности. Повторно используются [годовой расчёт](reporting.md), [аналитика](reporting-analytics.md) и [операционные источники](reporting-operations.md). Новые маршруты — /api/v1/management в legacy API. Текущие маршруты годового отчёта и их пользователи сохраняются.

Вход — действующий HR/admin legacy с областью установки и явным contour=training|working. Чужие источники не подключаются по произвольному клиентскому пути. Для демонстрации достаточно учебной БД или существующих пакетов; доступность сервисов коллег не требуется. Новые источники при отсутствии подключения обозначаются unavailable.

## 4A · текущая работа и факты интервью

GET /management/overview?from=YYYY-MM-DD&to=YYYY-MM-DD&contour=... возвращает {generated_at,period:{from,to,timezone:"Europe/Moscow"},source:{system:"legacy-hr",contour},funnel,interviews,sources}.

Границы периода — from включительно, to исключительно. funnel переиспользует существующую операционную воронку с её единицами и временем среза. Не переписывать её правила. interviews содержит held_count (held_at в периоде), no_answer_count (attempt_at в периоде, result=no_answer), by_interviewer [{interviewer_user_id,held_count,outcomes:{continue,stop,pending}}], undated_count и пояснение охвата. Поля новых исходов появились в функциональной задаче второй волны; при отсутствии нужной схемы источник интервью даёт unavailable.

Считаются зарегистрированные встречи соответствующего контура. Строка без held_at не превращается в проведённый разговор. Разные звонки одного отклика считаются отдельно, число откликов с разговором при необходимости дедуплицируется по application_id и подписывается своей единицей. Число no_answer не прибавляется к held_count.

sources содержит описание доступности журналов и времени обновления; Workforce/Hiring/практика указываются unavailable, если реального входа нет. Ноль наблюдённых записей обозначается как «0 зарегистрировано в этом журнале», без заявления о полном кадровом охвате организации. Обычная роль department в этой новой агрегированной операции недопустима до отдельной реализации её ограниченного представления.

Демо — учебные завершённая встреча, no_answer и незавершённая запись. Сводка различает их. При отсутствии источника нет выдуманного положительного результата. Нагрузка/полный набор тестов не нужны.

## 4B · годовой выпуск из доступных фактов

POST /management/annual-reports принимает {year,observed_until,contour,coverage:{applications:{complete_intervals,comparable_to_previous_year},phone_interviews:{complete_intervals,comparable_to_previous_year}},confirmation_basis}. year — целое, observed_until дата, интервалы по действующему reporting контракту. confirmation_basis объясняет, кто и на каком основании заявил покрытие. По умолчанию интервалы пустые и полнота не обещается.

Сервис выбирает свои разрешённые Application source=response и Interview, формирует существующий входной пакет с техническими ключами, реальными датами и contour. ФИО, контакты и тексты резюме в пакет не добавляются. Форматы/правила существующего loader/engine сохраняются. Рабочая область берётся из серверной настройки, не из произвольного пути клиента. Противоречия источника возвращаются как ошибка подготовки, а не исправляются вымышленной датой.

После расчёта ответ 201 {snapshot_id,mode,year,generated_at,coverage_summary,report_url,xlsx_url}. GET /management/annual-reports/{snapshot_id} и GET /management/annual-reports/{snapshot_id}/xlsx читают сохранённый выпуск с тем же доступом. Снимок и Excel используют одинаковое основание, поздняя поправка источника формирует новый выпуск. Технические ключи/хранилище существующего годового модуля повторно используются.

Проведение интервью берётся из его held_at. no_answer с датой попытки не превращается в phone_interviews_held. Уже действующие правила неполноты, сравнения лет и уникальных откликов не заменяются новым счётчиком.

Демо — небольшой учебный набор из первой части, выпуск, чтение JSON и Excel; при частичном периоде статус неполноты виден. Можно использовать существующий demo пакет для независимого первого запуска, явно указав источник. Большой архив, живая модель и новый брокер не нужны.

## 4C · плановый снимок потребностей

Первый плановый путь получает явно подготовленный HR снимок, без ожидания новых сервисных интеграций. POST /management/plans принимает {target_date,scope_label,needs:[{key,department_key,position_code,quantity:int>=1,source_reference}],people:[{person_ref:null|{system,id},record_ref:{system,id},label,contact_available:boolean}],matches:[{need_key,record_ref,readiness:confirmed|expected|similarity|unknown,basis}],coverage_note}.

Все ссылки указывают на входные записи. Источник и момент ввода сохраняются с актором. Readiness в этой версии — явно внесённое HR заключение для планирования с основанием; система не выводит его из поискового балла, курса или членства в резерве. Неизвестный контакт/идентичность имеет отдельное ограничение.

Снимок сохраняется неизменяемо. Ответ/GET /management/plans/{id} содержит по потребности количества по readiness, источники и предупреждения о неполноте. Для данного target_date все входные потребности трактуются как одновременные.

Независимое подтверждённое покрытие рассчитывается только для записей с подтверждённым person_ref, contact_available=true и ребром confirmed. Один человек может покрыть одну единицу потребности на выбранную дату. Потребность quantity разворачивается в соответствующее число мест. Использовать детерминированное максимальное паросочетание по этим рёбрам; порядок tie — стабильные ключи. Его результат — возможное покрытие, не назначение людей. Для записей с неразрешённой идентичностью дополнительно показать unresolved_records и предупреждение, не прибавлять их как подтверждённых уникальных людей.

GET /management/plans/{id}/summary даёт управленческую проекцию без имён/record_ref и первичных оснований. На первом пути обе операции доступны HR/admin своей установки. Представление для department будет отдельной задачей после проверки сопоставления организационных областей.

Демо — две потребности и один подтверждённый человек, подходящий обеим. Номинально обе имеют кандидата, независимое покрытие — одна из двух. Второй пример с дополнительным человеком и пересекающимися возможностями должен показать максимальное покрытие, а не ошибочный жадный выбор. Ожидаемый диплом находится в expected и не увеличивает confirmed.

Результат для руководства — объяснимый срез по предоставленному пакету. Автоматическая регистрация потребности, подключение чужих баз и подтверждение официального резерва сюда не включаются.
