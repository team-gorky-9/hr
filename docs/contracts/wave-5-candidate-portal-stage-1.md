# Волна 5 · собственное обращение кандидата · этап 1

Три небольших результата Ильи. Отдельная область candidate-portal внутри имеющегося подходящего приложения, /api/v1/candidate-requests. Допускается существующий вход Hiring/fixture-акторы. Полноценная регистрация по почте остаётся в согласованном бэклоге; в демонстрации два разных candidate-актора проверяют объектные права.

Пути ниже указаны относительно /api/v1. Например, POST /candidate-requests означает полный адрес /api/v1/candidate-requests.

## Общая граница

Собственное обращение принадлежит актору входа, а не переданному в теле actor_id. Кандидатская запись legacy и личный кабинет связываются только после явного подтверждения HR. Однофамильцы автоматически не объединяются. HR читает обращения своей разрешённой организации; кандидат — свои. Ответ кандидату содержит разрешённое объяснение без внутренней оценки и полного отзыва департамента.

UUID, revision и expected_revision, история и понятные 404/409/422. Файлы локальные и привязаны к обращению. Этап 1 сохраняет реальный собственный путь и явные ручные внешние подтверждения, не изображая автоматическую связь всех систем.

## 5A · подать обращение или выбрать вакансию

Request = {id,organization_id,author_actor_id,vacancy_ref:null|{system,id,revision},message,contact:{channel,value},revision,status:draft|submitted|needs_information|ready|forwarded|closed|withdrawn,created_at,submitted_at:null|timestamp}. Контакт — сообщение самого кандидата, HR видит происхождение, его актуальность не объявляется внешне проверенной.

| Операция | Результат |
|---|---|
| POST /candidate-requests {vacancy_ref?,message,contact} | Собственный draft |
| PATCH /candidate-requests/{id} {expected_revision,message?,contact?,vacancy_ref?} | Правка черновика |
| POST /candidate-requests/{id}/documents | multipart резюме/дополнение → сохранённый неизменяемый документ своего обращения |
| POST /candidate-requests/{id}/submit {expected_revision} | Снимок собственной подачи, номер и статус |
| GET /candidate-requests и GET /candidate-requests/{id} | Собственные обращения или разрешённая очередь HR |
| GET /candidate-requests/{id}/documents/{document_id}/content | Свой файл либо уполномоченный HR этого обращения |

Публичные вакансии можно читать по существующему каталогу либо предоставить помеченный учебный снимок. Если цель закрыта/неопределённа, обращение принимается с вопросом цели и не становится автоматически откликом. Подача без вакансии допустима. При отсутствии профессиональных сведений HR запрашивает их следующим шагом.

Демо — один кандидат подал по вакансии, другой без цели. Каждый видит свой номер и файлы. Чужой ID не открывается. Новое резюме сохраняется отдельным документом.

## 5B · уточнить сведения и передать на рассмотрение

POST /candidate-requests/{id}/information-request {expected_revision,public_message,requested_items} выполняет HR, статус needs_information. POST /candidate-requests/{id}/addendum {expected_revision,text,document_ids} выполняет автор; сохраняются предыдущие материалы и новая подача.

POST /candidate-requests/{id}/ready {expected_revision,review_basis} выполняет HR после проверки достаточности. Кандидат видит готовность своего обращения к следующему рассмотрению, а не положительную оценку пригодности.

POST /candidate-requests/{id}/record-consideration {expected_revision,candidate_ref,application_ref,selected_vacancy_ref,identity_basis,source_reference} сохраняет HR после фактической регистрации в подборе. Ссылки на чужие системы явно маркируются system. Источник подтверждения manual-confirmed, имя/телефон сами по себе не являются правилом автоматического объединения. При недоступной соседней системе состояние остаётся ready до регистрации подтверждения.

Перед выбором вакансии кандидат может согласовать её через POST /candidate-requests/{id}/choose-vacancy {expected_revision,vacancy_ref}. Применимые условия показываются из точной версии. Если заявитель принёс только ссылку на объявление, HR сначала определяет цель и запрашивает сведения человека.

Демо — запрос резюме/уточнения, дополнение, выбор вакансии и ручная регистрация принятого рассмотрения. Наличие двух совпавших имён оставляет вопрос идентичности HR. Для независимого показа допускается явно учебная ссылка результата, без заявления реального соединения.

## 5C · объяснить исход и дать вернуться к обращению

POST /candidate-requests/{id}/public-outcome {expected_revision,outcome:continue|declined|no_open_opportunity|completed,public_explanation,next_action:null|string,source_reference} выполняет HR в permitted состоянии ready/forwarded. Внутренний диагноз или полный отзыв подразделения не копируются автоматически. Сохраняется автор решения и происхождение результата, а клиент видит согласованное публичное объяснение.

Для outcome=continue обращение остаётся forwarded с указанным следующим шагом, для остальных — closed. POST /candidate-requests/{id}/withdraw {expected_revision,reason} выполняет автор до закрытия. Остановки уже заведённого внешнего рассмотрения требуют подтверждения у его владельца; локальный отзыв не объявляет автоматическое закрытие чужого дела.

В локальном кабинете создаётся сообщение о запросе/результате. GET /candidate-requests/{id}/messages доступен автору/HR дела. POST /candidate-requests/{id}/messages/{message_id}/read подтверждает чтение автором. Это доставка внутри кабинета. Email/СЭД/RabbitMQ не нужны и не объявляются работающими.

Демо — кандидат возвращается, видит запрос, затем понятный итог и следующий шаг. Прочтение помечает сообщение. Другая учётка не получает текст. Если подходящих вакансий сейчас нет, это отдельный исход; сохранение в кадровом архиве требует своего основания и действия.
