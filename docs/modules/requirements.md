# Загрузка и утверждение профилей требований

Публичный модуль — `app.requirements`. Он проверяет профиль, создаёт черновик и отдельно утверждает его через существующий repository. Оценщик, HTTP API и LLM при загрузке не вызываются. Правила строк и `params` остаются в [общих схемах](../../app/schemas/requirements.py); схема БД и миграции не менялись. [Контракт загрузчика](../contracts/requirement-loader.md) описывает новый вход, [контракт профилей](../contracts/requirements.md) — содержание правил.

## Два режима загрузки

| Вход | Команда | Версия |
|---|---|---|
| Один нормализованный `requirement-draft/1.0` | `load` | Следующий номер внутри должности и контура; поле `version` во входе запрещено |
| Пакет `requirement-profile-review/0.2`, манифест и оригиналы | `load-package` | Точная версия из пакета; повтор отклоняется, существующая версия не перезаписывается |

Для обоих режимов нужны миграции до текущего `head`, справочники из `app.db.seed` и `DATABASE_URL`. По умолчанию CLI выполняет проверку с записью во временной транзакции и **откатывает** её. UUID из `dry_run` не существует после завершения. `--commit` сохраняет результат. Только `load --approve` или отдельная команда `approve` могут утверждать профиль.

## Автономный пример py-9001

Из корня продукта:

```powershell
uv sync --locked
uv run alembic upgrade head
uv run python -m app.db.seed
uv run python -m app.requirements load fixtures/requirement_profiles/py-9001.draft.json
uv run python -m app.requirements load fixtures/requirement_profiles/py-9001.draft.json --commit
```

Последняя команда печатает JSON с `profiles[0].profile_id`, версией, статусом `draft`, `is_synthetic=true` и числом строк. Файл не требует внешних документов. Его условие 24 месяцев и индикатор API-тестов соответствуют `fixtures/assessment/py-9001.json`; порог не становится правилом реальной ДИ.

Для утверждения **заранее нужен существующий активный пользователь HR или admin**. После интеграции backend-02 seed создаёт учётки стенда `hr_demo`, `dept_demo`, `admin_demo`; учебный пример можно утвердить от `hr_demo`. Ни загрузчик, ни команда утверждения не создают пользователя и не повышают его роль. В рабочей среде оператор указывает фактический логин уполномоченного кадровика:

```powershell
uv run python -m app.requirements approve <UUID_ИЗ_СОХРАНЁННОЙ_ЗАГРУЗКИ> --approver <ЛОГИН_HR> --basis "Проверен учебный пример py-9001" --commit
```

Создать и утвердить следующую версию одной транзакцией:

```powershell
uv run python -m app.requirements load fixtures/requirement_profiles/py-9001.draft.json --approve --approver <ЛОГИН_HR> --basis "Проверена следующая учебная версия" --commit
```

Например, первая загрузка создаёт draft v1. HR утверждает v1; повторная загрузка создаёт draft v2, оставляя v1 действующей. Утверждение v2 архивирует v1 только в учебном контуре. Если утверждение запрещено, составная команда не сохраняет и новый черновик. Для оценки используется та же версия профиля: [прогон py-9001](assessment.md#сквозной-прогон-py-9001-qa-01). При базовом тексте стаж неизвестен, индикатор подтверждается цитатой, численный уровень отсутствует.

## Пакет из реальных документов

Готовый пакет содержит консультанта v4 и Python v5, оба рабочие **черновики**. Для него нужны четыре исходных файла под корнем распакованной папки «Кадры», пути и SHA-256 — в `sources.json`:

```powershell
uv run python -m app.requirements load-package fixtures/requirement_profiles/profiles.draft.json fixtures/requirement_profiles/sources.json "<КОРЕНЬ_ИСХОДНИКОВ>"
# --commit добавляется явно, если оператор хочет сохранить черновики.
```

`--synthetic fixtures/requirement_profiles/synthetic/cases.json` дополнительно импортирует учебный профиль v2 из пакета. Он отличается ключами от автономного py-9001. Это **тот же учебный контур Python**: пакеты с уже занятой версией конфликтуют, поэтому для сравнения двух учебных наборов нужна чистая тестовая БД либо согласованная новая версия пакета.

Проверяются пути внутри корня, хеши настоящих байтов, полный набор абзацев DOCX/TXT и цитаты по `paragraph_ids`. Цитата может объединять несоседние абзацы; их фрагменты сохраняются дословно. У нормализованного входа проверяются UUID источника и наличие фрагментов цитаты в сохранённом тексте в исходном порядке. Поля ревью остаются в JSON-пакете; CLI возвращает счётчики `review_fields`. Неизвестное поле не игнорируется. Старое `score: null` в учебном пакете принимается как отсутствие шкалы; численное значение отклоняется.

Весь пакет атомарен: ошибка второй должности не оставляет первую или новые документы. Импорт пакета никогда не утверждает профили. Успешная проверка источников не означает содержательного принятия требований кадровиком.

## Устройство и транзакции

| Файл | Назначение |
|---|---|
| `schemas.py` | Строгая оболочка входа, существующие типизированные строки, общие дубли и группы |
| `service.py` | Создание следующей версии, утверждение, чтение действующего профиля |
| `package.py` | Проверка оригиналов, преобразование пакета 0.2, сохранение фиксированных версий |
| `errors.py` | `RequirementError(code, message, path)` без входных значений и SQL в публичном сообщении |
| `cli.py` | Аргументы, существующий утверждающий пользователь, внешняя транзакция, JSON-ответ |
| `app/schemas/requirement_groups.py` | Общая структурная проверка `same_as`; старый импорт из assessment сохранён |

Сервис принимает SQLAlchemy `Session`, выполняет `flush` и SAVEPOINT, но не `commit`. Вызывающий владеет внешней транзакцией. Как обычно для `Session.begin_nested()`, посторонние pending-изменения вызывающего предварительно flush-ятся; перед вызовом следует завершить их проверку. Ошибка операции откатывает её SAVEPOINT, не отменяя ранее успешные операции вызывающего.

Перед выбором версии и утверждением блокируется строка должности `FOR UPDATE`; это сериализует операции нового сервиса до завершения внешней транзакции. Для нескольких должностей пакет берёт блокировки в порядке кодов. Старые прямые вызовы repository сохраняют гарантии уникальных ограничений БД; их интерфейс не меняется. Стандартный режим — PostgreSQL READ COMMITTED; при иной изоляции вызывающий должен обрабатывать сериализационные конфликты.

Существующие `scripts.load_requirement_profiles`, `scripts.load_synthetic_profile`, `scripts.approve_profile` сохранены для текущих потребителей. Первый сохраняет фиксированные версии, второй по прежнему **сразу делает commit**; безопасный по умолчанию новый маршрут — `python -m app.requirements`. Старые вспомогательные функции не получают новые гарантии валидации автоматически. Проверка реального пакета сравнивает все сохранённые строки с прежним преобразованием.

## Проверка

`TEST_DATABASE_URL` должен указывать на отдельную БД с pgvector, имя оканчивается `_test`: pytest удаляет её схему.

```powershell
uv run pytest tests/test_requirements_public.py -q
uv run pytest -q -rs
uv run python -m scripts.verify_requirement_profiles --card-schemas
# DATABASE_URL — отдельная подготовленная тестовая БД без версий пакета:
uv run python -m scripts.verify_requirements_loader --source-root "<КОРЕНЬ_ИСХОДНИКОВ>"
```

Последний скрипт проверяет настоящие байты и эквивалентность прежнему преобразованию, печатает счётчики и версии PostgreSQL/pgvector, всегда откатывает транзакцию. Результаты и ограничения актуального запуска — [интеграционный отчёт requirements-01](../reports/requirements-01-integration.md).

## Пакет шести должностей

`scripts.load_all_six_profiles` — обёртка над публичным `load_package`, с фиксированным каталогом `fixtures/requirement_profiles/all_six/`. Сначала проверяет состав шести должностей и байты семи документов, затем загружает пакет одной транзакцией. По умолчанию откатывает изменения; `--commit` сохраняет draft. Дополняет отчёт публичного CLI кодами должностей и перечнями источников. Утверждение остаётся отдельным `app.requirements approve`; скрытого создания пользователей нет.

Все данные доступны в самостоятельном клоне, без исходного архива и LLM. [Инструкция и решения HR](../../fixtures/requirement_profiles/all_six/README.md) · [Проверки пакета и жизненного цикла](../../tests/test_all_six_profiles.py).
