# Модуль HTTP API (`app/api/`, `app/main.py`)

Отдаёт фронтенду вакансии, отклики, оценки и очищенные тексты (Этап 1, только чтение) и ведёт действия кадровика (Этап 2, backend-02): перевод этапов с историей, кросс-оценки, кадровый резерв, воронка. Персональные данные кандидатов не отдаёт ни один маршрут.

Контракт: [api.md](../contracts/api.md) v0.4. Опирается на [database.md](../contracts/database.md) v1.8 (резерв — раздел 19): контуры п. 2.6.1, цитаты п. 2.11, внешние отклики п. 4.5. Владелец — Денис. Потребители — фронтенд (Ася) и сквозная сборка `qa-01`.

## Запуск

Сначала база, миграции и справочники, как в [README](../../README.md#запуск-базы). Затем:

```bash
uv run uvicorn app.main:app --reload
```

- Swagger UI: http://127.0.0.1:8000/docs
- схема OpenAPI: http://127.0.0.1:8000/openapi.json
- проверка: `curl http://127.0.0.1:8000/api/v1/health` → `{"status": "ok", "db": "ok"}`

Переменные `.env` (образец — `.env.example`):

| Переменная | Зачем | По умолчанию |
|---|---|---|
| `DATABASE_URL` | база приложения | `postgresql+psycopg://hr:hr@localhost:5432/hr` |
| `CORS_ORIGINS` | адреса фронтенда, которым браузер разрешит запросы; JSON-список | `["http://localhost:5173", "http://127.0.0.1:5173"]` (Vite) |

## Маршруты Этапа 1

| Маршрут | Что отдаёт |
|---|---|
| `GET /api/v1/health` | `200 {"status":"ok","db":"ok"}`; база недоступна → `503 {"status":"error","db":"error"}` |
| `GET /api/v1/vacancies?contour=` | вакансии, утверждённый профиль в контуре, число откликов контура |
| `GET /api/v1/vacancies/{id}/applications?contour=&stage_code=&formal_result=&formal_preliminary=&assessment_status=` | отклики вакансии со статусом оценки |
| `GET /api/v1/applications/{id}` | карточка отклика: этап, обезличенная карточка кандидата, оценка с цитатами |
| `GET /api/v1/candidate-texts/{id}` | версия очищенного текста для панели источника |

`contour`: `working` (по умолчанию) — реальные кандидаты и рабочий профиль; `training` — учебные кандидаты (`py-9001`) и учебный профиль.

## Маршруты Этапа 2 (backend-02)

Все требуют заголовок `X-User-Login` с ролью `hr` или `admin`; `department` получает `403` (см. «Кто действует»).

| Маршрут | Что делает |
|---|---|
| `GET /api/v1/references/stages`, `…/rejection-reasons` | справочники этапов и причин отказа |
| `GET /api/v1/applications/{id}/history` | события этапов по `seq`, `last_seq` для формы |
| `POST /api/v1/applications/{id}/stage` | перевод этапа с `expected_seq`; `201` + событие |
| `GET /api/v1/candidates/{id}/cross-assessments` | оценки по всем утверждённым профилям контура кандидата (модель чтения ai-02) |
| `POST /api/v1/reserve` | включение в резерв; `201` новая запись, `200` + `created: false` — действующая прежняя |
| `POST /api/v1/reserve/{id}/withdraw` | отзыв основания резерва |
| `GET /api/v1/positions/{id}/reserve?contour=` | действующий резерв на должность |
| `GET /api/v1/analytics/funnel?contour=&vacancy_id=&position_id=&period_from=&period_to=` | воронка: этапы сейчас, закрытия за период |

Передача руководителю и ответ департамента — `workflow-01`, гайд интервью — `interview-01`. Задел этих частей сохранён в локальной ветке `wip/workflow-01-interview-01-groundwork`.

## Как устроено

```
app/main.py           create_app(): CORS, обработчики ошибок, роутеры (API и годовой отчёт)
app/api/routes.py     маршруты: разбор параметров → вызов services / workflow
app/api/services.py   чтение Этапа 1: статус оценки, сборка AssessmentOut, границы цитат UTF-16, comparison
app/api/workflow.py   backend-02: этапы, история, кросс-оценки, резерв, воронка
app/api/auth.py       учебная авторизация: пользователь из X-User-Login, проверка роли
app/api/schemas.py    DTO запросов и ответов (они же схема OpenAPI)
app/api/errors.py     ApiError и единый формат {"error": {code, message, details}}
```

### Кто действует (учебная авторизация)

`auth.current_user` читает `X-User-Login`, находит активного пользователя в `users`, роль берёт из базы. `require_role(...)` — зависимость FastAPI, которая отвечает `403 FORBIDDEN_ROLE`. Учётки стенда `hr_demo`, `dept_demo`, `admin_demo` создаёт `seed_demo_users()` в `app/db/seed.py`. Это подпись действия в журналах, а не защита: пароля нет. Маршруты Этапа 1 пользователя не требуют. Маршруты backend-02 требуют, в том числе на чтение: область доступа департамента не согласована, поэтому `department` по прямому ID ничего не получает.

### Транзакции записи

Правила данных — в `repository.py` (он не делает commit). Сервис записи в `workflow.py` проверяет вход, вызывает функцию репозитория и сам делает `session.commit()`. Если что-то упало, сессия закрывается без commit и всё откатывается. В тестах commit превращается в точку сохранения внешней транзакции (`tests/conftest.py`).

### Перевод этапа: две вкладки, 422 или 409

1. Ввод (`422`): неизвестный этап или причина, причина не к отказу, нет причины при `rejected`/`withdrawn`.
2. `session.refresh(application, with_for_update=True)` блокирует строку отклика, затем последний `seq` истории сравнивается с `expected_seq`. Не совпал — `409 STALE_STAGE_FORM`. Блокировка держится до commit, поэтому вторая вкладка ждёт первую и видит уже новый `seq`.
3. `move_application` проверяет правило этапов; его отказ — `409 STAGE_TRANSITION_CONFLICT` с текстом правила.

Отклик не `response` (`history`, `manual`) — `409 NOT_WORKING_APPLICATION` до всех проверок.

### Резерв

`repository.reserve_candidate` возвращает `(запись, created)`. Цель — должность, иначе направление. Одну активную запись на цель держат частичные уникальные индексы (БД v1.8). Вставка идёт в точке сохранения: если параллельный запрос успел первым, вставка ждёт его commit, ловит нарушение уникальности и возвращает его запись. Истёкшая активная запись при новом включении закрывается (`expired`). Действующая запись определяется одним условием `active_reserve_condition(today)`: его используют список резерва и (в `search-01`) фильтр поиска. API дополнительно требует `reason` и `contact_basis`, отклоняет прошедший срок и исходный отклик другого кандидата или не `response`.

### Воронка

Выборка — отклики `source = response` на вакансии платформы от кандидатов контура, с фильтром по вакансии или должности. `current_count` — `GROUP BY current_stage_code`; `reached_count` — разные `application_id` в `stage_events` по `to_stage_code`. Закрытия — события перехода в `hired`/`rejected`/`withdrawn` за период: даты включительно, сутки по `Europe/Moscow`, полуинтервал `[начало from; начало дня после to)`. Без причины — строка `reason_code = null`. `open_waits` — `null` до `workflow-01`. Годовой отчёт `app/reporting` строится из выгрузки без базы, поэтому эта воронка его подсчёты не повторяет.

### Гайд интервью и ответы (interview-01)

`app/api/interview.py`, контракт `interview.md` v0.4 §4.

**`POST` гайда** идёт в три шага:
1. **Ранний выход без модели.** Если `request_id` уже встречался, возвращается тот же гайд. Если у открытой встречи есть гайд и `regenerate = false`, возвращается он. При `regenerate = true` с прежней базовой оценкой, версией профиля и отпечатком рубрики тоже возвращается существующий гайд.
2. **Чтение и модель.** Оценка отклика берётся так же, как в карточке: `resolve_states` + применимость. `app.interview.build_guide(record_calls=False)` собирает гайд, затем `session.rollback()` завершает чтение. Сессия держит соединение пула на время вызова модели — допущение v0.4.
3. **Короткая транзакция записи.**
   - Перепроверить текущую оценку (id, базовую, профиль) и версии строк рубрики, иначе `409 ASSESSMENT_CHANGED`.
   - Сохранить новые строки рубрики (`ON CONFLICT DO NOTHING`).
   - Вопросы ядра взять из сохранённой рубрики, чтобы они совпадали у всех кандидатов.
   - Открыть встречу и записать версию гайда.
   - Записать журнал вызовов модели и сделать `commit`.

**Чтение гайда** берёт из снимка вопросы, пробелы сверх бюджета и базовую оценку. Остальное считается по текущей оценке пары:
- **`stale_reason`** по порядку проверки: `profile_changed`, `assessment_stale`, `assessment_changed` (другая базовая оценка), `rubric_changed`;
- **`status` вопроса:** `resolved` — все формальные требования из `sources` подтверждены не по резюме; `answered` — есть свой или перенесённый ответ; иначе `open`;
- **`document_requests`** — `assemble_gaps` по текущей оценке.

**Ответы и подтверждение.** Проверки и запись делают `repository.add_interview_answer` и `confirm_formal_check`. API превращает `RuleConflict` в `404`/`409` с кодом контракта, остальные `RepositoryError` — в `422`. Клиент модели — зависимость `get_llm_client`, в тестах её подменяют на `FakeLLMClient`.

### Кросс-оценки

Маршрут вызывает модель чтения ai-02 `app.assessment.cross.cross_assessments` (Илья) и только проверяет DTO, превращает `candidate_not_found` в `404` и упорядочивает строки. Своей логики выбора профилей, актуальности и цитат в API нет.

### Общие правила с модулем оценки

`resolve_states` (статус оценки), `AssessmentState`, `AssessmentStatus`/`StaleReason`, сбор текстов цитат и границы UTF-16 живут в `app/assessment/state.py`. API (`services.py`, `schemas.py`) и кросс-оценка импортируют их оттуда. `services.utf16_offset` — обёртка над `verification.utf16_offsets`. Это одно правило на проект, поэтому статус пары «кандидат × профиль» в списке откликов, в карточке и в рекомендациях совпадает.

### Статус оценки (`assessment_status`)

Считает одна функция `services.resolve_states()`, общая для списка и карточки:

1. В контуре нет утверждённого профиля → `no_approved_profile`. В списке `formal_result = null`, у карточки `assessment = null`.
2. Есть текущая оценка по утверждённому профилю:
   - карточка этой оценки извлечена из текущей версии очищенного текста → `ready`;
   - иначе → `stale`, `stale_reason = "text_changed"`.
3. Есть только текущая оценка по **другому** профилю этой должности в том же контуре (утверждённый профиль с тех пор сменился) → `stale`, `stale_reason = "profile_changed"`.
4. Иначе → `not_assessed`: `formal_result = null`. Это не то же самое, что `formal_result = "unknown"`.

При `stale` значения прежней оценки отдаются (`formal_result`, `overall_score`), а интерфейс показывает предупреждение. Фильтры списка сравнивают отдаваемые значения.

Запросов на список фиксированное число (отклики, текущие тексты, оценки с карточками, текущие карточки), без N+1. Пагинации нет: на вакансию до ~430 откликов.

### Цитаты для браузера

В базе `start`/`end` — кодовые точки (срез Python `text[start:end]`). JavaScript считает строки в UTF-16, и символ вне BMP (эмодзи) там занимает две позиции. Поэтому каждая цитата (`EvidenceOut`) несёт ещё `utf16_start`/`utf16_end` = `len(text[:i].encode("utf-16-le")) // 2`. Считаются они по тому тексту, на который ссылается цитата. У устаревшей оценки это прежняя версия текста, и фронтенд берёт её через `GET /candidate-texts/{candidate_text_id}` из цитаты.

Пример `py-9001` (C5): текст `🙂 Написал API-тесты для сервиса заявок.`. Цитата `start=2, end=39`, в UTF-16 `utf16_start=3, utf16_end=40`.

### Ошибки

Полный список кодов Этапа 2 — в контракте (п. 3.2–3.5). Основные:

| Код HTTP | `error.code` | Когда |
|---|---|---|
| 401 | `USER_REQUIRED`, `UNKNOWN_USER` | нет `X-User-Login` или пользователь неизвестен/отключён |
| 403 | `FORBIDDEN_ROLE` | роль не допускает действие |
| 409 | `STALE_STAGE_FORM`, `STAGE_TRANSITION_CONFLICT`, `NOT_WORKING_APPLICATION`, `RESERVE_NOT_ACTIVE` | форма устарела; переход запрещён правилом этапов; отклик не `response`; запись резерва уже закрыта |
| 404 | `VACANCY_NOT_FOUND`, `APPLICATION_NOT_FOUND`, `CANDIDATE_TEXT_NOT_FOUND`, `CANDIDATE_NOT_FOUND`, `POSITION_NOT_FOUND`, `RESERVE_NOT_FOUND` | нет сущности с таким UUID |
| 404 | `NOT_FOUND` | нет такого маршрута |
| 422 | `VALIDATION_ERROR` | неверный UUID или значение query; `details.errors` — где и что (без повтора ввода) |
| 422 | `UNKNOWN_STAGE_CODE`, `UNKNOWN_REJECTION_REASON`, `REJECTION_REASON_REQUIRED`, `REJECTION_REASON_NOT_ALLOWED`, `RESERVE_*`, `APPLICATION_OF_OTHER_CANDIDATE`, `WITHDRAW_REASON_REQUIRED`, `INVALID_PERIOD` | ошибка ввода (см. контракт) |
| 500 | `INTERNAL_ERROR` | непредвиденная ошибка; текст исключения клиенту не отдаётся, он в журнале сервера |
