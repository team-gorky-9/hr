# Поиск кандидатов по профессиональному опыту

Рабочая точка входа — [POST /api/v1/search/candidates](../contracts/search.md) в `app.main:app`. Поиск читает только текущий очищенный текст и выводит один результат на запись кандидата. Для поиска по фразе BM25 и локальный E5 дают независимые ранги, затем RRF объединяет допустимые попадания. Для поиска по фильтрам ответ содержит основания из карточки и актуального резерва. Формальный допуск к вакансии вычисляет оценщик.

## Запуск

1. Поднимите PostgreSQL с расширением `vector` и примените миграции. См. [README](../../README.md#запуск-базы). В уже настроенной среде достаточно `uv sync --locked` и `uv run --no-sync alembic upgrade head`.
2. Для плотной ветки установите CPU-сборку PyTorch в виртуальное окружение продукта и подключите закреплённые зависимости. Офлайн-тесты и лексический поиск запускаются с базовыми зависимостями.

   ```text
   uv pip install --python .venv --index-url https://download.pytorch.org/whl/cpu torch==2.14.1
   uv pip install --python .venv -r requirements-search.txt
   uv run --no-sync python -m app.search prepare-model
   ```

   `prepare-model` заранее скачивает ревизию E5 и токенизатор в кэш Hugging Face. В закрытой среде перенесите кэш той же ревизии и при необходимости укажите `HF_HUB_CACHE`. В процессе поиска модель использует локальные файлы. На сервере можно дополнительно задать `HF_HUB_OFFLINE=1`. По умолчанию работает лексическое ранжирование. Для эксперимента или учебного демо задайте `HR_SEARCH_SEMANTIC_ENABLED=true` в окружении приложения. При включении используется калиброванный порог `HR_SEARCH_DENSE_THRESHOLD=0.94`, если среда не задаёт другой. Выделенный рабочий ключ хранится в `HR_SEARCH_WORK_TOKEN` и подставляется доверенным прокси. Развёртывание связанных маршрутов чтения требует закрытого периметра. Учебный контур использует синтетические записи и доступен без ключа.

3. Индексировать контур после импорта или после смены правил очистки.

   ```text
   uv run --no-sync python -m app.search index --contour training
   uv run --no-sync python -m app.search index --contour working --candidate-code py-0005
   ```

   Команда использует `DATABASE_URL`, принимает `--contour training|working` и опциональный `--candidate-code`. На каждый текущий текст одна транзакция с блокировкой. Повторная индексация совпадающего набора сообщает `unchanged`. Параллельный запуск той же модели не создаёт дублей. При сбое уже завершённые документы сохранены, повтор безопасен. При смене текущего текста старые векторы сразу выпадают из поиска, лексика использует новый текст. После повторной индексации плотная ветка использует новую версию. При неполном индексе поле `semantic_status` показывает `partial`. Если веса или индекс недоступны, запрос по тексту использует лексическую ветку.

## HTTP на учебных данных

Поместите `DATABASE_URL` отдельной учебной базы в окружение команды. `load-demo` загружает 18 синтетических резюме с версиями очищенного текста, карточками, тремя примерами откликов одного кандидата и активными записями резерва. Идентификаторы базы создаются заново в каждой установке. Повторная загрузка той же фикстуры безопасна.

```text
uv run --no-sync alembic upgrade head
uv run --no-sync python -m app.search load-demo
uv run --no-sync python -m app.search index --contour training
uv run --no-sync uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Запрос `{"contour":"training","query":"анализ и согласование требований к ИС"}` возвращает `search-9001` с фрагментом из опыта и данными двух активных откликов и одной исторической записи. В отдельном терминале `uv run --no-sync python scripts/check_search_demo.py` повторяет путь через реальные HTTP, проверяет точный термин, структурированные основания, пустой результат и ошибки `401`/`422`. Для самостоятельной проверки подсветки откройте `GET /api/v1/candidate-texts/{candidate_text_id}` и исполните `text.slice(evidence.utf16_start, evidence.utf16_end) === evidence.fragment` в JavaScript. Python-границы считаются от начала всего документа в кодовых точках; браузерные — в элементах UTF-16.

Техническая проверка E5 использует `--probe-semantic` и явно заданные `HR_SEARCH_SEMANTIC_ENABLED=true`, `HR_SEARCH_DENSE_THRESHOLD=0.78` в окружении запущенного сервера. Она проверяет попадание `search-9013` от настоящих локальных векторов через PostgreSQL по запросу «электронная маршрутизация жалоб населения». На калибровке v1 этот диагностический порог дал выдачу на обоих запросах без ответа. Он воспроизводит технический проход через плотную ветку.

## Сравнение

```text
uv run --no-sync python -m app.search evaluate --repeats 3 --output search-evaluation.json
```

Разметка [search-01-synthetic-v1](../../fixtures/search/synthetic-v1.json) закреплена до замера коммитом `4007052`. В ней 18 искусственных документов, шесть калибровочных и восемь контрольных запросов. Лексика, dense и гибрид используют одинаковые границы фрагментов и ограничения входа. Слои API и PostgreSQL в этом сравнении заменены расчётом exact cosine в памяти. Интеграционный тест проверяет SQL-оператор отдельно.

Файл [замера](search-evaluation-v1.json) содержит сетку порогов, счётчики, запросы, ошибочные попадания и границы. Код замера `64f5470`, SHA-256 данных `6a6e13d64caa212d1bb1fb131f2fd220a18eb5c0d49d4f661c88e8a67d7c275a`. Порог плотной ветки `0.94` выбран по шести калибровочным запросам до прохода по контрольным. В контрольной группе значения Precision@5 и @10 рассчитаны на уровне кандидата со знаменателем 5/10, включая короткую выдачу. Запросы без ответа учитываются отдельно.

| Способ | Precision@5 | Precision@10 | Релевантные выданы / пропущены в топ-10 | Ложная выдача на запросах без ответа | Валидные границы | Медиана / p95 тёплого поиска, мс |
|---|---:|---:|---:|---:|---:|---:|
| BM25 | 0,20 | 0,10 | 6 / 1 | 0 / 2 | 7 / 7 | 4,33 / 5,66 |
| Dense E5 | 0,00 | 0,00 | 0 / 7 | 0 / 2 | 0 цитат | 27,50 / 44,47 |
| Hybrid | 0,20 | 0,10 | 6 / 1 | 0 / 2 | 7 / 7 | 30,32 / 41,17 |

Гибрид не нашёл дополнительного кандидата на запросе с перефразированием и не выполнил критерий выбора. BM25 и гибрид пропустили `search-9013` по «маршрутизация заявлений горожан по подразделениям». В запросе «анализ и согласование требований к ИС» они также вернули лишний `search-9003` с фрагментом «Снабжение торговой сети, запрос коммерческих предложений и согласование договоров». Все шесть цитат релевантных кандидатов совпали с разметкой лексики и гибрида.

Среда второго замера: Windows 11, Python 3.13.6, 16 логических CPU, `OMP_NUM_THREADS=4`, `MKL_NUM_THREADS=4`, Torch 2.14.1 CPU, Transformers 5.20.2. Холодная инициализация модели заняла 26,25 с, векторизация 25 фрагментов — 0,35 с. Медиана и p95 относятся к 24 повторным запросам ранжирования, включая подготовку текста и вычисление вектора запроса, без HTTP и БД. Приёмка на стенде требует отдельно измерить задержку exact cosine, время переиндексации и качество на рабочем архиве с разметкой кадровика.

## Тесты

`uv run pytest -q tests/test_search_core.py tests/test_search_http.py` проверяет Unicode, нарезку, токены, прямые отрицания, ранги и OpenAPI/HTTP. Для проверки реального SQL с pgvector запустите `uv run pytest -q tests/test_search_postgres.py` с `TEST_DATABASE_URL` отдельной БД, имя которой заканчивается `_test`. В SQL-тесте детерминированный энкодер проверяет поведение на заданных векторах, настоящая E5 — через учебный запуск выше. В обоих прогонах контролируются разделение контуров, номера законов, `401`/`422`/`503`, источники отклика и актуальность.

## Устройство

- `text.py` режет очищенный текст на секции и проверяемые окна. Вместе с архивным подвалом исключается блок истории общения. Технические токены, включая `25-ФЗ`, `1С`, `C++`, `Node.js`, сохраняются целиком. Правило прямого отрицания ограничено короткими выражениями из контракта.
- `ranking.py` применяет обязательные точные термины, проверяет значимые лексемы и ранжирует лучшие фрагменты кандидатов до RRF. В лексике BM25 использует `k1=1.2`, `b=0.75`, отсечку `1e-9`. Векторы использует exact cosine с отсечкой до ранжирования. В RRF `k=60`.
- `storage.py` выбирает текущий текст, актуальную карточку, доступный резерв и метаданные откликов. Чтение проходит в одном снимке с режимом read only. Модель E5 имеет размерность 384, в ключ индекса входят ревизия `614241f622f53c4eeff9890bdc4f31cfecc418b3` и `chunk-v1`. Перед операцией расстояния PostgreSQL проверяет размерность вектора, а при сопоставлении проверяются версия и дословность фрагмента. Индекс HNSW не используется в этой конфигурации.
